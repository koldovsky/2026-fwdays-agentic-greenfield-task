# Specification: Dashboard and Analytics (`dashboard-analytics`)

## Glossary and Definitions

| Термін | Визначення |
| :--- | :--- |
| **Dashboard** | Веб-інтерфейс особистого кабінету користувача, доступний за маршрутом `/dashboard`. |
| **Precision Hub** | Дизайн-система інтерфейсу, що базується на стилі Pure Light Mode з високим рівнем контрасту, мінімалістичними тінями, монохромними рамками та чіткою типографікою. |
| **Recharts** | Бібліотека для побудови реактивних інтерактивних графіків у React. |
| **Apps Script Code** | Готовий скрипт для Google Таблиць, який містить API-ключ користувача та URL-адресу платформи для автоматичного відправлення конверсій до `ingestion-api`. |
| **CRM / Telephony Credentials** | Чутливі дані доступу (хост, логін, пароль, API-токени), які використовуються для майбутніх інтеграцій. |

## Scope & Non-Goals

### Bounded Scope
- Створення сторінки особистого кабінету користувача за адресою `/dashboard`.
- Форма для збереження інтеграційних доступів до CRM та телефонії з обов'язковим шифруванням паролів та API-ключів за алгоритмом AES-256-GCM.
- Generator інтеграційного скрипта Google Apps Script та генерація/перегляд API-ключа.
- Інтерактивні інструкції для GA4, Google Ads, Google Cloud та Binotel.
- Панель аналітики з вибором періоду (до 14 місяців) та сумарними картками метрик.
- Лінійний графік динаміки конверсій та два кругових графіки розподілу за джерелами та каналами.
- Таблиця останніх 100 конверсій з пагінацією та фільтрами за джерелом та каналом.
- Забезпечення продуктивності рендерингу та побудови звітів з локальної БД ≤ 500 мс.

### Non-Goals
- Реалізація фонових процесів, які самі підключаються до CRM чи телефонії для імпорту (кабінет лише зберігає ці доступи для майбутнього використання).
- Експорт звітів у PDF чи Excel (поза межами MVP).
- Зберігання даних конверсій за період, більший ніж 14 місяців.

## Requirements

### Requirement: CRM and Telephony Access Form (FR-DASH-01)
Система SHALL надавати форму в особистому кабінеті для внесення та збереження доступів користувача до CRM (URL, логін, пароль) та Телефонії (URL, логін, пароль, REST API ключі). Чутливі поля (паролі, API-ключі) MUST бути зашифровані за допомогою AES-256-GCM перед збереженням у базі даних.

#### Scenario: Успішне збереження та шифрування доступів
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач заповнює поля доступу CRM та телефонії на сторінці кабінету та натискає "Зберегти"
- **THEN** система валідує URL-адреси (вони мають бути коректними посиланнями з обов'язковим протоколом `https://`)
- **AND** якщо чутливі поля (пароль CRM, пароль телефонії, API-ключ телефонії) не були змінені користувачем (містить маску `••••••••` або надіслані порожніми), система зберігає їхні діючі зашифровані значення в базі даних без перезапису
- **AND** якщо чутливі поля оновлюються, система шифрує їх за допомогою алгоритму AES-256-GCM (з використанням `ENCRYPTION_KEY` з конфігурації)
- **AND** якщо користувач видаляє доступ до сервісу (очищує логін/URL або натискає кнопку видалення доступу), система записує NULL у відповідні поля бази даних
- **AND** система оновлює запис користувача в таблиці `users` в БД
- **AND** повертає повідомлення про успішне збереження без виведення шифрованих значень у відповіді API

#### Scenario: Помилка валідації полів доступу
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач вносить невалідні значення (наприклад, URL з `http://` або некоректний формат посилання) та натискає "Зберегти"
- **THEN** система відхиляє запит, повертаючи статус `400 Bad Request`
- **AND** надає структурований JSON з описом помилок для кожного невалідного поля
- **AND** клієнтський інтерфейс відображає повідомлення про помилки під відповідними полями

#### Scenario: Системна помилка при збереженні або ширфуванні
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** виникає збій при роботі з БД або під час шифрування (наприклад, невалідний або відсутній `ENCRYPTION_KEY`)
- **THEN** система безпечно перериває операцію, логує деталі помилки на сервері без витоку стек-трейсів клієнту
- **AND** повертає клієнту загальне повідомлення про помилку зі статусом `500 Internal Server Error`

#### Scenario: Відображення збережених налаштувань
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач завантажує сторінку налаштувань інтеграцій
- **THEN** система зчитує дані з таблиці `users`
- **AND** перевіряє наявність збережених паролів та API-ключів без їх дешифрування на сервері (якщо відповідне поле в базі даних не порожнє та не дорівнює NULL, то дані наявні)
- **AND** відображає текстові поля (логіни, URL) як є, а паролі/ключі маскує (наприклад, відображає плейсхолдер у вигляді крапок або пусте поле з позначкою "збережено")

### Requirement: Instructions Accordion (FR-DASH-02)
Система SHALL відображати детальні інтерактивні інструкції з налаштування GA4, Google Ads, Google Cloud (включаючи вимоги до надання прав Editor, Project IAM Admin, BigQuery Admin для сервісного акаунту `auto@acontrol.pro`) та Binotel.

#### Scenario: Перегляд інструкцій користувачем
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач переходить до розділу інструкцій у кабінеті
- **THEN** sistema рендерить структурований віджет (наприклад, Accordion) з окремими кроками для кожної платформи
- **AND** інструкція для Google Cloud чітко вказує email сервісного акаунту `auto@acontrol.pro` та необхідні ролі (Editor, Project IAM Admin, BigQuery Admin)

### Requirement: API Key and Apps Script Generator (FR-DASH-03)
Система SHALL дозволяти користувачеві генерувати та копіювати унікальний API-ключ, а також автоматично формувати готовий код Google Apps Script, підставляючи в нього цей API-ключ та поточний домен платформи.

#### Scenario: Генерація нового API-ключа
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач натискає кнопку "Згенерувати новий API-ключ" та підтверджує дію
- **THEN** система створює новий випадковий рядок (API-ключ довжиною ≥ 32 символи)
- **AND** обчислює його SHA-256 хеш
- **AND** зберігає цей хеш у полі `api_key_hash` таблиці `users`
- **AND** показує відкритий API-ключ користувачеві ОДИН РАЗ із кнопкою швидкого копіювання
- **AND** оновлює згенерований Apps Script код у клієнтському стані, підставляючи відкритий API-ключ замість плейсхолдера

#### Scenario: Копіювання коду Apps Script
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач відкриває вкладку Apps Script у кабінеті
- **THEN** система відображає блок коду (textarea або code block) з кнопкою "Копіювати"
- **AND** якщо хеш API-ключа наявний у базі даних користувача, блок коду містить поточний домен (обчислений на основі змінної оточення `NEXT_PUBLIC_APP_URL` або динамічно з заголовків `host`/`x-forwarded-host` запиту, наприклад, `https://acontrol.pro/api/conversions`) та текстовий плейсхолдер замість API-ключа (наприклад, `YOUR_API_KEY`) із підказкою вставити свій згенерований раніше ключ (через неможливість його відновлення з хешу)
- **AND** якщо API-ключ ще ніколи не був згенерований, система виводить інструкцію згенерувати ключ спочатку

### Requirement: Analytics Period Filter (FR-DASH-04)
Система SHALL дозволяти користувачеві обирати період аналітики (за замовчуванням останні 30 днів) з обмеженням максимум у 14 місяців для побудови всіх аналітичних звітів на дашборді.

#### Scenario: Зміна періоду аналітики
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач обирає новий період (наприклад, останні 90 днів або custom діапазон) через селектор дат
- **THEN** система перевіряє, що початкова дата не перевищує 14 місяців від поточної дати
- **AND** система перевіряє, що кінцева дата не є ранішою за початкову дату (`endDate >= startDate`), та що обидві дати є коректними ISO-8601/timestamp значеннями
- **AND** система перевіряє, що початкова та кінцева дати не знаходяться в майбутньому відносно поточної дати в Київському часовому поясі (`Europe/Kyiv`)
- **AND** для запиту в БД дати `startDate` та `endDate` трансформуються в часові межі (timestamp boundaries: з 00:00:00 для початкової дати до 23:59:59.999 для кінцевої дати за Київським часом)
- **AND** система перевантажує дані для карток метрик, графіків та таблиці на основі вибраного діапазону дат

### Requirement: Summary Metric Cards (FR-DASH-05)
Система SHALL обчислювати та відображати 4 ключові метрики за вибраний період: загальна кількість отриманих конверсій, сумарна цінність конверсій (у валюті UAH), кількість рекламних конверсій (`is_ad_conversion = true`) та їхній відсотковий відносний показник від загальної кількості.

#### Scenario: Розрахунок показників метрик
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** завантажується аналітика для обраного періоду
- **THEN** система виконує агрегаційні запити до таблиці `conversions` для поточного користувача
- **AND** розраховує:
  - `Total Conversions` (COUNT усіх записів)
  - `Total Value` (SUM поля `conversion_value`)
  - `Ad Conversions` (COUNT записів, де `is_ad_conversion = true`)
  - `Ad Conversions %` (відношення `Ad Conversions` до `Total Conversions` помножене на 100, округлене до одного десяткового знаку)
  - **AND** якщо конверсій немає, відображає нульові значення (`0`, `0 ₴`, `0`, `0%`)

### Requirement: Conversion Trend Line Chart (FR-DASH-06)
Система SHALL відображати лінійний графік (Line Chart) динаміки передачі конверсій за обраний період (із динамічним групуванням за днями/тижнями/місяцями), використовуючи бібліотеку Recharts.

#### Scenario: Рендеринг лінійного графіка динаміки
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** завантажується аналітика з наявними конверсіями
- **THEN** система приводить значення `conversionTime` кожного запису до Київського часового поясу (`Europe/Kyiv`) та групує записи конверсій за датою: за днями для періодів до 90 днів включно, та за тижнями/місяцями для довших періодів (до 14 місяців)
- **AND** будує графік з двома лініями: "Загальні конверсії" та "Рекламні конверсії"
- **AND** при наведенні на точку графіка відображає спливаючу підказку (Tooltip) з точними даними на цей інтервал

#### Scenario: Поведінка лінійного графіка при відсутності даних
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** завантажується аналітика за період, коли конверсій немає
- **THEN** система відображає пусту сітку графіка без ліній із текстовим повідомленням про відсутність даних (наприклад, "Немає даних про конверсії за цей період")

### Requirement: Distribution Pie Charts (FR-DASH-07)
Система SHALL відображати дві кругові діаграми (Pie Charts) розподілу конверсій за обраний період:
1. За рекламними джерелами (`ad_source` - Google Ads, Meta Ads, Organic, інше).
2. За каналами (`channel` - Вебсайт, Телефонія, Месенджери, інше).

#### Scenario: Рендеринг діаграм розподілу
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** завантажується аналітика з наявними конверсіями
- **THEN** система приводить значення `ad_source` та `channel` до відповідних стандартних категорій, виконуючи нечутливий до регістру мапінг (будь-яке значення, що містить "google" або "gads" — до "Google Ads"; "meta" або "facebook" — до "Meta Ads"; "organic" — до "Organic"; решта — до "інше". Для каналів: значення "web" або "website" — до "Вебсайт"; "phone" або "telephony" — до "Телефонія"; "messenger" або "telegram" — до "Месенджери"; решта — до "інше"), а потім групує їх
- **AND** будує дві кругові діаграми з легендами та різними кольорами для секторів
- **AND** сектори відображають відсоткову частку кожного джерела/каналу

#### Scenario: Поведінка кругових діаграм при відсутності даних
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** завантажується аналітика за період, коли конверсій немає
- **THEN** система відображає заглушки кругових діаграм (сірі кола) із повідомленням "Немає даних" або "Дані відсутні"

### Requirement: Conversions Log Table (FR-DASH-08)
Система SHALL відображати таблицю останніх 100 конверсій користувача за обраний період із можливістю пагінації (по 10 записів на сторінку) та швидкої фільтрації за рекламним джерелом (`ad_source`) та каналом (`channel`). З метою забезпечення точності аналітики, фільтрація виконується на серверній стороні (API приймає параметри `adSource` та `channel` та виконує SQL-запит з відповідними фільтрами, повертаючи 100 останніх відповідних конверсій), а пагінація виконується на клієнтській стороні в межах завантажених 100 записів.

#### Scenario: Фільтрація та пагінація таблиці конверсій
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач обирає фільтр за джерелом (наприклад, `Google Ads`) або каналом
- **THEN** клієнт робить запит до API з передачею вибраних фільтрів
- **AND** система повертає до 100 останніх записів з бази даних, які відповідають вказаним фільтрам за обраний період
- **AND** таблиця відображає отримані записи, а пагінація автоматично перераховує сторінки на основі фактично завантажених записів

#### Scenario: Поведінка таблиці при відсутності даних
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** завантажується аналітика за період або з фільтрами, коли відповідних конверсій немає
- **THEN** таблиця відображає один порожній рядок із текстом "Конверсій не знайдено за обраний період"

### Requirement: Dashboard Load Performance (NFR-PERF-02)
Час повного завантаження сторінки особистого кабінету та рендерингу графіків з локальної бази даних SHALL становити ≤ 500 мс для 95% запитів (p95).

#### Scenario: Швидке завантаження звітів
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач завантажує сторінку `/dashboard`
- **THEN** система використовує оптимізовані індекси в таблиці `conversions` (`idx_conversions_user_id_conversion_time`) для швидкого фетчингу та агрегації даних
- **AND** під час очікування відповіді від API кабінет відображає Skeleton loaders для віджетів та графіків, щоб уникнути різких стрибків інтерфейсу

### Requirement: Subscription Management Form (FR-SUB-01, FR-SUB-06, FR-SUB-07)
Система SHALL надавати вкладку "Оплата" в особистому кабінеті для перегляду та керування підпискою користувача, відображаючи інформацію про поточний статус (Active, Paused, Suspended, Cancelled), обраний тариф ($10.99/міс або $120/рік в еквіваленті UAH), дату закінчення періоду, а також дозволяти купувати, призупиняти або скасовувати підписку.

#### Scenario: Перегляд інформації про підписку
- **GIVEN** користувач є автентифікованим та має активну сесію особистого кабінету
- **WHEN** користувач відкриває вкладку "Оплата"
- **THEN** система зчитує статус підписки з таблиці `subscriptions` в БД
- **AND** відображає деталі діючої підписки: назву плану, ціну, термін дії, а також статус та збережену замасковану картку (наприклад, `**** **** **** 1234`), якщо вона токенізована

#### Scenario: Оформлення нової підписки (Checkout)
- **GIVEN** користувач є автентифікованим, має активну сесію та не має активної підписки
- **WHEN** користувач обирає тариф (Місячний або Річний) та натискає "Оплатити"
- **THEN** система ініціює створення інвойсу через Monobank Acquiring API (`POST /api/billing/invoice/create`) із параметром `saveCardData: { saveCard: true }`
- **AND** перенаправляє користувача на отриманий лінк оплати (`pageUrl`)
- **AND** після успішної оплати та повернення користувача на сайт, статус підписки відображається як `Active`

#### Scenario: Тимчасове призупинення підписки (Пауза)
- **GIVEN** користувач має активну підписку зі статусом `Active`
- **WHEN** користувач натискає кнопку "Пауза" та підтверджує свій вибір
- **THEN** система надсилає запит до API (`POST /api/billing/pause`)
- **AND** оновлює статус підписки в базі даних (система вимикає автосписання, токен картки зберігається, сервіс працює до кінця сплаченого періоду, після чого статус переходить у `Paused`)
- **AND** інтерфейс оновлює статус та показує повідомлення про призупинення автопродовження

#### Scenario: Скасування підписки
- **GIVEN** користувач має активну підписку
- **WHEN** користувач натискає кнопку "Скасувати підписку"
- **THEN** система відображає модальне попередження про зупинку автоматичної передачі конверсій та можливу втрату ефективності реклами
- **WHEN** користувач підтверджує скасування
- **THEN** система надсилає запит до API (`POST /api/billing/cancel`)
- **AND** оновлює статус підписки на `Cancelled`
- **AND** видаляє токен картки з гаманця Monobank (`DELETE /api/merchant/wallet/card`) після закінчення сплаченого періоду
- **AND** оновлює інтерфейс, відображаючи дату завершення дії послуги

### Requirement: Brand Tone and Localization Constraints (NFR-I18N-01, BC-BRAND-01)
Усі елементи інтерфейсу особистого кабінету (кнопки, вкладки, форми, інструкції, графіки) та системні повідомлення мають бути реалізовані виключно українською мовою. Усі тексти інтерфейсу, інструкцій та повідомлень про помилки повинні бути сформульовані у спокійному, практичному та ввічливому тоні без використання знаків оклику.

#### Scenario: Перевірка локалізації та тональності повідомлень
- **WHEN** будь-який елемент інтерфейсу особистого кабінету або системне повідомлення виводиться користувачу
- **THEN** весь текст має бути написаний українською мовою.
- **AND** тексти не повинні містити знаків оклику ("!").
