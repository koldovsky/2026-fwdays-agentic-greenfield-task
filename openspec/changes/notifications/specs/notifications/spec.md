# Specification: Telegram Notifications (`notifications`)

## Glossary and Definitions
- **Telegram Bot API**: HTTP-інтерфейс для взаємодії з Telegram-ботом.
- **Admin Chat**: Telegram-чат (ідентифікатор якого задано через `TELEGRAM_ADMIN_CHAT_ID`), куди надсилаються службові повідомлення для адміністратора.
- **Client Card (Картка клієнта)**: Зведений набір даних про користувача (Ім'я, Сайт, Телефон, Пошта, Час, Нік у Telegram) для інформування адміністратора.
- **Kyiv Time (Київський час)**: Часовий пояс `Europe/Kyiv` (UTC+2 взимку, UTC+3 влітку), який використовується для відображення дати та часу у сповіщеннях.
- **Date Format (Формат дати)**: Формат представлення дати та часу у сповіщеннях адміністратора: `ДД.ММ.РРРР ГГ:ХХ` (наприклад, `04.07.2026 19:30`).

## Scope & Non-Goals

### Bounded Scope
- Реалізація механізму відправки сповіщень адміністратору в Telegram-чат при зміні статусів підписки користувача.
- Реалізація сервісних сповіщень користувачам в Telegram-чат при першій оплаті, неуспішному автосписанні або призупиненні сервісу.
- Ізоляція помилок взаємодії з Telegram API (неблокуюче відправлення).
- Дотримання вимог локалізації (виключно українська мова) та тону бренду (нейтральний тон без знаків оклику).

### Non-Goals
- Налаштування користувачем фільтрації або вимкнення окремих сповіщень через веб-кабінет.
- Інтеграція інших каналів зв'язку (SMS, Email, Push-сповіщення).
- Моніторинг доставки повідомлень з боку користувача.
- Налаштування безпеки Telegram-чату адміністратора (поза рамками цієї зміни, за винятком конфігурації ID).

## Requirements

### Requirement: FR-NOTIF-01: Сповіщення адміністратора в спеціальний чат
Адміністратор системи MUST отримувати сповіщення про події клієнтів у Telegram-чат, ідентифікатор якого задано в конфігурації через змінну `TELEGRAM_ADMIN_CHAT_ID`. Повідомлення MUST містити поточну дату та картку клієнта: Ім'я, Сайт, Телефон, Пошта, Час, Нік у Telegram. Дата та час MUST відображатися за київським часом (Kyiv Time) у форматі `ДД.ММ.РРРР ГГ:ХХ`.

#### Scenario: Надсилання картки клієнта адміністратору
- **WHEN** виникає подія підписки клієнта
- **THEN** система формує повідомлення з поточною датою, назвою події, ім'ям клієнта, сайтом, телефоном, поштою, часом та юзернеймом Telegram і надсилає його до чату адміністратора
- **AND** дата та час у повідомленні формовані за київським часом у форматі `ДД.ММ.РРРР ГГ:ХХ`

### Requirement: FR-NOTIF-02: Події підписок для сповіщення адміністратора
Система SHALL сповіщати адміністратора про наступні події життєвого циклу підписки: «Нова підписка», «Платіж отримано», «Скасування підписки», «Пауза підписки», «Поновлення підписки» (коли клієнт відновлює скасовану чи призупинену підписку).

#### Scenario: Сповіщення про нову підписку
- **WHEN** користувач вперше оформлює підписку
- **THEN** система надсилає адміністратору повідомлення з назвою події «Нова підписка» та деталями тарифного плану

#### Scenario: Сповіщення про платіж клієнта
- **WHEN** успішно обробляється платіж клієнта
- **THEN** система надсилає адміністратору повідомлення з назвою події «Платіж отримано» та сумою оплати в UAH

#### Scenario: Сповіщення про скасування підписки
- **WHEN** користувач скасовує підписку
- **THEN** система надсилає адміністратору повідомлення з назвою події «Скасування підписки»

#### Scenario: Сповіщення про паузу підписки
- **WHEN** статус підписки користувача змінюється на `Paused` (через активацію паузи користувачем)
- **THEN** система надсилає адміністратору повідомлення з назвою події «Пауза підписки»

#### Scenario: Сповіщення про поновлення підписки
- **WHEN** користувач поновлює скасовану чи призупинену підписку
- **THEN** система надсилає адміністратору повідомлення з назвою події «Поновлення підписки»

### Requirement: FR-NOTIF-03: Джерела даних для повідомлень адміністратора
Система SHALL збирати дані для повідомлень адміністратора з двох джерел: Телефон, Час та Ім'я клієнта MUST братися безпосередньо з вебхуку платіжної системи Monobank; Пошта, Сайт та Нік у Telegram MUST братися з бази даних профілю користувача.

#### Scenario: Формування даних повідомлення з вебхуку та бази даних
- **WHEN** надходить вебхук оплати від Monobank
- **THEN** система завантажує профіль користувача з бази даних за `userId` та поєднує його пошту, сайт і нік Telegram з ім'ям, телефоном та часом платежу з вебхуку для створення сповіщення
- **AND** якщо окремі поля профілю користувача в базі даних є порожніми (email, website, telegram username), замість них підставляється маркер «не вказано»

### Requirement: FR-NOTIF-04: Вітальне сповіщення користувача
Система SHALL надсилати привітальне повідомлення користувачеві в його особистий Telegram-чат при першому оформленні підписки. Повідомлення MUST містити посилання на інструкцію з налаштування інтеграції в особистому кабінеті.

#### Scenario: Перше оформлення підписки користувачем
- **WHEN** користувач успішно здійснює першу оплату підписки
- **THEN** система надсилає користувачеві в особистий чат привітання та посилання на інструкції в особистому кабінеті

### Requirement: FR-NOTIF-05: Попередження про невдале списання
Система SHALL надсилати повідомлення-попередження користувачеві в його особистий Telegram-чат у разі неуспішної спроби автоматичного списання плати за підписку. Повідомлення MUST містити інформацію про загрозу зупинки сервісу та посилання на особистий кабінет для оновлення платіжних даних.

#### Scenario: Неуспішне автоматичне списання
- **WHEN** автоматичний платіж через Monobank завершується помилкою
- **THEN** система надсилає користувачеві в особистий чат повідомлення про невдале списання із застереженням та посиланням на форму оновлення картки в кабінеті

### Requirement: FR-NOTIF-06: Сповіщення про фактичне призупинення сервісу
Система SHALL надсилати сповіщення користувачеві в його особистий Telegram-чат про фактичне призупинення надання послуг з передачі конверсій (через паузу, скасування підписки або тривалу несплату). Повідомлення MUST містити посилання на особистий кабінет для здійснення оплати та швидкого відновлення роботи.

#### Scenario: Призупинення сервісу через несплату, паузу або скасування
- **WHEN** статус підписки користувача змінюється на `Suspended`, `Paused` або `Cancelled` (після закінчення сплаченого періоду при скасуванні)
- **THEN** система надсилає користувачеві в особистий чат повідомлення про призупинення послуг з лінком на оплату або особистий кабінет

### Requirement: FR-NOTIF-07: Ізоляція помилок та ліміти запитів Telegram API
Функції надсилання сповіщень MUST працювати асинхронно та ізольовано від основних бізнес-транзакцій. Будь-які помилки відправки (наприклад, блокування бота користувачем, помилка `403 Forbidden`, мережеві таймаути або обмеження частоти запитів `429 Too Many Requests`) MUST перехоплюватися і логуватися без генерації помилок у викликаючому коді (вебхуках чи Cron-задачах). При відправці сповіщень під час масових операцій (Cron-задача) система MUST дотримуватися лімітів Telegram API (не більше 30 повідомлень на секунду загалом).

#### Scenario: Обробка помилок та лімітів Telegram API
- **WHEN** виникає помилка при виклику Telegram API (наприклад, статус `403` або `429`)
- **THEN** система записує інформацію про помилку у системний лог (`console.error` або `console.warn`)
- **AND** завершує виконання функції відправки успішно без переривання транзакції чи процесу білінгу

### Requirement: BC-BRAND-01: Спокійний та практичний тон повідомлень
Усі тексти сповіщень для адміністратора та користувачів MUST мати спокійний, практичний тон без знаків оклику.

#### Scenario: Валідація тону повідомлень
- **WHEN** система генерує будь-яке повідомлення сповіщення
- **THEN** згенерований текст не містить знаків оклику та використовує нейтральний бізнес-тон

### Requirement: NFR-I18N-01: Українська локалізація сповіщень
Усі повідомлення сповіщень MUST бути написані виключно українською мовою.

#### Scenario: Перевірка мови повідомлень
- **WHEN** система надсилає повідомлення користувачу або адміністратору
- **THEN** текст повідомлення складено виключно українською мовою

## Definition of Done (DoD)
Ця зміна вважається завершеною, коли:
1. Реалізовано функції відправки у `lib/notifications.ts`.
2. Інтегровано тригери сповіщень у вебхук Monobank та Cron-задачу автосписання.
3. Створено та запущено тестовий скрипт `scripts/test-notifications.ts`, який підтверджує коректність форматування, тону та обробки помилок.
4. Проект успішно компілюється (`npx tsc --noEmit`) та проходить перевірку лінтера (`npm run lint`).
