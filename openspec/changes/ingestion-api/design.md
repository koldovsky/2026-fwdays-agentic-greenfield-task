## Context

Платформа синхронізації конверсій вже має реалізовану інфраструктуру:
- **core-database**: Drizzle ORM зі схемами `users` (включаючи `api_key_hash`), `subscriptions`, `conversions`.
- **telegram-auth**: Повна реєстрація та авторизація через Telegram-бот.
- **billing-monobank**: Еквайринг Monobank, керування підписками, Cron-задачі автосписань.

Зараз потрібно створити REST API ендпоінт `POST /api/conversions`, який буде приймати дані з Google Таблиць через Apps Script. Це єдина точка входу зовнішніх даних у систему.

Існуюча архітектура:
- Next.js 16 App Router (Route Handlers)
- Таблиця `conversions` зі всіма необхідними полями та індексами вже створена
- `users.api_key_hash` зберігає SHA-256 хеш API-ключа (64-символьний hex)
- `subscriptions` з полями `status` та `currentPeriodEnd`
- Vercel Serverless environment з обмеженнями холодного старту

## Goals / Non-Goals

**Goals:**
- Безпечний REST API ендпоінт для прийому конверсій від Apps Script
- Автентифікація запитів за API-ключем через O(1) пошук за хешем
- Перевірка активності підписки перед прийомом
- Batch insert для забезпечення p95 ≤ 200 мс
- Автоматичне очищення даних, старших за 14 місяців

**Non-Goals:**
- Rate limiting для API-ключів (можна додати пізніше)
- Real-time webhook після прийому конверсій
- Підтримка форматів, крім JSON
- Дедуплікація конверсій (Apps Script відповідає за унікальність)

## Decisions

### 1. Автентифікація через SHA-256 хеш
**Рішення**: Використовувати `crypto.createHash('sha256').update(apiKey).digest('hex')` для хешування отриманого `X-API-Key` та пошуку за `api_key_hash` в таблиці `users`.

**Альтернативи:**
- HMAC-based підпис запитів — надлишково для M2M API з фіксованим ключем
- bcrypt-хешування — повільне для кожного запиту (100+ мс), не підходить для p95 ≤ 200 мс

**Обґрунтування**: SHA-256 хешування виконується за ~0.1 мс, а пошук за індексованим `api_key_hash` (unique index) — за O(1). API-ключі достатньо довгі (32+ символів) для стійкості до brute-force.

### 2. Batch INSERT через Drizzle ORM
**Рішення**: Використовувати `db.insert(conversions).values(records)` для вставки всього масиву конверсій одним SQL-запитом.

**Альтернативи:**
- Transaction з окремими INSERT — повільно, багато round-trips
- Raw SQL COPY — складніше, Drizzle batch insert достатньо ефективний

**Обґрунтування**: Drizzle ORM компілює batch values insert у один `INSERT INTO ... VALUES (...), (...), (...)` SQL-запит, що мінімізує мережевий overhead та укладається в 200 мс навіть для 500 записів.

### 3. Валідація через вбудований парсер
**Рішення**: Ручна валідація з масивом помилок замість Zod або іншої схеми.

**Альтернативи:**
- Zod schema — додаткова залежність, збільшує bundle size
- JSON Schema (ajv) — надлишково для простої flat-структури

**Обґрунтування**: Структура конверсії проста (12 полів, 4 обов'язкові). Ручна валідація дає повний контроль над форматом помилок та мінімізує холодний старт serverless функції. Повертаємо масив помилок з індексом запису для зручності дебагу в Apps Script.

### 4. Cron-ендпоінт через Vercel Cron Jobs
**Рішення**: Створити `GET /api/conversions/cleanup` з авторизацією через `CRON_SECRET` та налаштувати Vercel Cron у `vercel.json`.

**Альтернативи:**
- Окремий скрипт `scripts/cleanup-conversions.ts` із зовнішнім планувальником — додаткова інфраструктура
- pg_cron на рівні бази — не доступний на Neon Free Tier

**Обґрунтування**: Vercel Cron Jobs інтегровані у платформу, не потребують додаткового коду для планувальника, та працюють на Free/Hobby tier. Захист через `CRON_SECRET` — стандартна практика Vercel.

### 5. Підписка: перевірка статусу та періоду
**Рішення**: Єдиний SQL-запит `SELECT status, currentPeriodEnd FROM subscriptions WHERE userId = ? ORDER BY createdAt DESC LIMIT 1` для отримання останньої підписки. Перевірка у коді: `status === 'active' && currentPeriodEnd > now`.

**Альтернативи:**
- JOIN з users — ускладнює запит без потреби, userId вже відомий з автентифікації
- Кешування статусу підписки — додаткова складність, підписка рідко змінюється

**Обґрунтування**: Простий SELECT за індексованим `userId` з LIMIT 1 виконується за 1-5 мс. Перевірка `currentPeriodEnd` окремо від `status` дозволяє розрізнити ситуацію, коли cron ще не встиг оновити статус при закінченні періоду.

## Risks / Trade-offs

1. **[Холодний старт Serverless]** → Перший запит після неактивності може перевищити 200 мс. Мітигація: мінімальний bundle (без Zod/ajv), lazy import тільки потрібних модулів.

2. **[Batch insert великих пакетів]** → 500 записів можуть генерувати великий SQL-запит. Мітигація: ліміт у 500 записів, що покриває типовий usecase Apps Script (100-200 за раз).

3. **[Відсутність rate limiting]** → Теоретично один користувач може генерувати надмірне навантаження. Мітигація: ліміт пакету 500 записів; повноцінний rate limiting — у наступних ітераціях.

4. **[Очищення великих обсягів]** → При першому запуску cleanup може видалити багато записів. Мітигація: `DELETE ... WHERE conversionTime < ... LIMIT 10000` з повторним запуском, щоб уникнути тривалих locks на рівні БД.
