## Context

Ми розробляємо систему автентифікації користувачів для платформи aControl. Особливість системи полягає в тому, що веб-реєстрація повністю заблокована доти, доки користувач не зв'яже свій Telegram-акаунт через спеціального бота. Вхід на сайт виконується безпарольно за допомогою Magic Link або 6-значного одноразового коду (OTP), які надсилаються в Telegram. Вся комунікація має відповідати стилістиці "Precision Hub" та обмеженням мови/тону (українська мова, спокійний практичний тон без знаків оклику).

## Goals / Non-Goals

**Goals:**
- Забезпечити безпечне пов'язування Telegram-акаунта з профілем на етапі реєстрації.
- Налаштувати Route Handler для обробки вебхуків Telegram API у безсерверному (Serverless) середовищі.
- Реалізувати генерацію QR-кодів та посилань для переходу до бота.
- Реалізувати діалог збору даних (`email`, `website_url`) ботом з валідацією.
- Реалізувати перенаправлення сайту після завершення реєстрації в боті.
- Реалізувати вхід через Magic Link та 6-значний OTP-код.
- Дотриматися вимог дизайну та копірайтингу (українська мова, відсутність знаків оклику).

**Non-Goals:**
- Інтеграція реклами або CRM на цьому етапі.
- Використання сторонніх сервісів авторизації чи кук для відстеження.

## Decisions

### 1. Метод інтеграції з Telegram API
- **Варіант А**: Постійне опитування (Long Polling) у фоновому процесі.
- **Варіант Б**: Вебхуки (Webhooks) через Next.js Route Handler (`POST /api/telegram/webhook`).
- **Рішення**: **Варіант Б**. Для розгортання в Serverless-середовищі (Vercel) тривалі фонові процеси не підтримуються. Route Handlers забезпечують миттєву обробку повідомлень, не споживають ресурсів під час простою та легко масштабуються. Для захисту ендпоінту буде використовуватися заголовок `X-Telegram-Bot-Api-Secret-Token`.

### 2. Збереження стану тимчасової реєстрації
- **Варіант А**: Тимчасовий кеш в пам'яті (in-memory).
- **Варіант Б**: Нова таблиця `pending_registrations` у PostgreSQL.
- **Рішення**: **Варіант Б**. Serverless-середовище має стан cold-start і кілька паралельних інстансів, тому зберігати стан у пам'яті неможливо. Таблиця `pending_registrations` міститиме:
  - `id` (uuid)
  - `token` (uuid, унікальний реєстраційний токен)
  - `telegram_id` (bigint, заповнюється ботом після сканування)
  - `telegram_username` (varchar)
  - `email` (varchar)
  - `website_url` (varchar)
  - `is_completed` (boolean)
  - `expires_at` (timestamp)
  - `created_at` (timestamp)

### 3. Автоматичний редірект після бот-реєстрації
- **Варіант А**: WebSockets / Server-Sent Events (SSE).
- **Варіант Б**: Коротке опитування (Short Polling) з боку клієнта на сторінці реєстрації до ендпоінту `/api/auth/poll-registration?token=<token>`.
- **Рішення**: **Варіант Б**. Веб-сокети потребують постійного з'єднання, що складно підтримувати у чистих Serverless-системах. SSE потребує тривалого HTTP-з'єднання. Коротке опитування (раз на 3 секунди) є надзвичайно стійким, простим у реалізації та не створює значного навантаження. Для безпеки відразу після успішної перевірки токена та створення сесії запис про цей токен у `pending_registrations` анулюється або видаляється, запобігаючи його повторному використанню.

### 4. Реалізація OTP-кодів
- **Варіант А**: Додавання колонки `otp_code` в існуючу таблицю `magic_links`.
- **Варіант Б**: Створення окремої таблиці `otp_codes`.
- **Рішення**: **Варіант Б**. Таблиця `magic_links` має тип UUID для токенів і не підходить для збереження 6-значних чисел. Створення окремої таблиці `otp_codes` розділяє логіку Magic Link та OTP-входу. Таблиця міститиме `id`, `user_id` (з cascade delete), `code` (varchar 6), `attempts` (integer, за замовчуванням 0), `expires_at`, `is_used` та `created_at`. Код анулюється при успішній автентифікації або після 3 невдалих спроб перевірки (`attempts >= 3`).

## Risks / Trade-offs

- **[Risk]** Спам вебхуків Telegram фіктивними запитами.
  - **Mitigation**: При встановленні вебхука задати `secret_token` у запиті до Telegram, і перевіряти його значення в заголовку `X-Telegram-Bot-Api-Secret-Token` при кожному виклику нашого Route Handler на відповідність значенню `TELEGRAM_BOT_WEBHOOK_SECRET`.
- **[Risk]** Підбір 6-значних OTP-кодів методом перебору (brute-force).
  - **Mitigation**: Встановити обмеження у 3 спроби верифікації коду, після чого він стає недійсним. Додатково впровадити rate limiting на рівні API Route Handler для запитів на авторизацію.
- **[Risk]** Перебір електронних адрес користувачів (User Enumeration) на формі входу.
  - **Mitigation**: API авторизації та інтерфейс сторінки `/login` завжди повертають нейтральне повідомлення успіху про те, що код надіслано в бот, незалежно від наявності користувача в системі.
- **[Risk]** Користувач закриває сторінку реєстрації на сайті, але проходить опитування в боті.
  - **Mitigation**: Бот успішно створює користувача в базі даних та надсилає йому Magic Link. Користувач зможе увійти пізніше, перейшовши за надісланим Magic Link.
- **[Risk]** Перевищення лімітів безкоштовної БД Neon через велику кількість незавершених реєстрацій.
  - **Mitigation**: Додати автоматичне очищення прострочених записів у `pending_registrations` та `otp_codes` (наприклад, видалення старих записів при генерації нових токенів або регулярну крон-задачу).
