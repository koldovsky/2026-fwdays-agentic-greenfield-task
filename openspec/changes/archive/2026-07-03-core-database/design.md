## Context

Даний проект є новоствореним (greenfield) веб-додатком на базі Next.js 16 (App Router), який потребує надійного та безпечного рівня збереження даних. Системі необхідно оперувати даними користувачів, інформацією про сесії, статусами підписок (інтеграція з Monobank Acquiring) та детальними логами конверсій. Оскільки додаток розгортається в безкоштовному/дешевому серверлесс-середовищі (Vercel Serverless + Neon Serverless Postgres / Supabase), дизайн має мінімізувати споживання ресурсів та кількість активних підключень до БД. Також, згідно з вимогами безпеки, паролі до CRM та ключі API телефонії повинні зберігатися в зашифрованому вигляді.

## Goals / Non-Goals

**Goals:**
- Налаштувати Drizzle ORM у проекті Next.js з підтримкою TypeScript.
- Розробити строго типізовану схему таблиць: `users`, `magic_links`, `sessions`, `subscriptions`, `conversions`.
- Реалізувати утиліти шифрування/дешифрування на базі алгоритму AES-256-GCM для захисту чутливих інтеграційних даних.
- Забезпечити сумісність з Serverless-платформами (Neon/Supabase) без вичерпання ліміту підключень (connection pooling).
- Налаштувати інструменти генерації та застосування міграцій бази даних (`drizzle-kit`).

**Non-Goals:**
- Створення користувацького інтерфейсу для введення облікових даних (це завдання для кабінету).
- Створення логіки синхронізації з CRM або телефоніями (буде реалізовано в окремих кроках).
- Автоматичний шедулінг щоденного видалення старих конверсій (це буде частиною кроку `ingestion-api`).

## Decisions

### 1. Вибір ORM та клієнта бази даних
- **Рішення**: Використання Drizzle ORM спільно з драйвером `@neondatabase/serverless` або стандартним `pg` (в залежності від обраного хостингу БД, Neon чи Supabase).
- **Обґрунтування**: Drizzle ORM забезпечує максимальну швидкість роботи та повну типізацію TypeScript без зайвого оверхеду, який притаманний важчим ORM на кшталт Prisma. Клієнт `@neondatabase/serverless` використовує WebSocket/HTTP з'єднання, що ідеально підходить для Serverless-середовища Vercel, запобігаючи проблемам із пулом з'єднань.
- **Альтернативи**: Prisma (відхилено через довший час cold start у serverless та генерацію важкого клієнта) або чистий SQL за допомогою `pg` (відхилено через відсутність вбудованої типізації та складність супроводу схем).

### 2. Структура схеми даних (Drizzle Schema)
- **Рішення**: Розподіл схеми на окремі файли в директорії `db/schema/` (`users.ts`, `magic_links.ts`, `sessions.ts`, `subscriptions.ts`, `conversions.ts`) з єдиною точкою експорту в `db/schema/index.ts`.
- **Обґрунтування**: Покращує читабельність та модульність коду в порівнянні з одним великим файлом `schema.ts`.
- **Альтернативи**: Один файл `schema.ts` (призводить до перенасичення коду при зростанні проекту).

### 3. Алгоритм шифрування
- **Рішення**: Використання вбудованого модуля `crypto` в Node.js для реалізації симетричного шифрування за стандартом **AES-256-GCM**.
- **Обґрунтування**: AES-256-GCM забезпечує як конфіденційність, так і автентичність даних (автентифіковане шифрування). Кожне шифрування генеруватиме випадковий 12-байтовий вектор ініціалізації (IV) та повертатиме 16-байтовий тег автентифікації. Зашифроване значення зберігатиметься у форматі `iv_hex:auth_tag_hex:encrypted_content_hex`. Ключ шифрування зчитуватиметься із змінної середовища `ENCRYPTION_KEY` (має бути довжиною 32 байти / 256 біт).
- **Альтернативи**: AES-256-CBC (менш безпечний через відсутність вбудованого контролю цілісності), bcrypt (не підходить, бо bcrypt є хеш-функцією в один бік, а нам потрібно дешифрувати дані для виконання інтеграційних запитів).

### 4. Керування міграціями
- **Рішення**: Використання `drizzle-kit` для автоматичної генерації SQL-файлів міграцій та локального накату міграцій через команду `drizzle-kit migrate`.
- **Обґрунтування**: Дозволяє мати версіоновані декларативні міграції, що зберігаються в системі контролю версій (`db/migrations`).

### 5. Безпека автентифікації REST API
- **Рішення**: Збереження унікального API-ключа користувача (`X-API-Key`) у вигляді хешу SHA-256 (`api_key_hash`) в таблиці `users`.
- **Обґрунтування**: Зберігання API-ключів у відкритому вигляді в базі даних є критичною вразливістю. Хешування запобігає витоку ключів у разі компрометації бази даних. При автентифікації запиту отриманий ключ хешується та порівнюється із збереженим значенням.

### 6. Розділення сесій та Magic Link токенів
- **Рішення**: Виділення Magic Link токенів в окрему таблицю `magic_links` з обмеженим терміном дії (expires_at) та обов'язковим статусом використання (is_used).
- **Обґрунтування**: Використання одного токена для Magic Link та сесії є небезпечним, оскільки Magic Link токен передається через URL та історію браузера. Після переходу за посиланням створюється нова чиста сесія у таблиці `sessions`, а Magic Link токен анулюється.

### 7. Типи даних Telegram ID та логіка рекурентних списань
- **Рішення**: 
  1. Використання типу `bigint` для поля `telegram_id` в таблиці `users`.
  2. Додавання полів `last_invoice_id` (для кореляції вебхуків monobank), `failed_attempts_count` та `last_failed_attempt_at` до таблиці `subscriptions`.
  3. Створення композитного індексу `(user_id, conversion_time)` та звичайного індексу на `created_at` у таблиці `conversions`.
- **Обґрунтування**: Telegram ID переросли межі стандартного 32-бітного цілого числа. Поля спроб необхідні для реалізації 2 додаткових спроб списання протягом 48 годин згідно з FR-SUB-05. Індекси забезпечують швидкість аналітичних запитів (≤ 500 мс на p95) та ефективність фонового очищення застарілих даних.

## Risks / Trade-offs

- **[Risk] Вичерпання лімітів підключень до бази даних (connection pool exhaustion)**
  → *Mitigation*: Впровадження лінивої ініціалізації клієнта Drizzle у файлі `db/index.ts`. Використання Neon Connection Pooling (через транзакційний порт `5432` або WebSockets-драйвер `@neondatabase/serverless`) для ефективного перевикористання з'єднань.
- **[Risk] Втрата ключа шифрування `ENCRYPTION_KEY`**
  → *Mitigation*: Якщо ключ буде втрачено або змінено, розшифрувати існуючі CRM/телефонійні паролі буде неможливо. Ми задокументуємо необхідність бекапу ключа в менеджері секретів (Vercel env variables). При втраті ключа користувачам доведеться повторно ввести доступи в кабінеті.
