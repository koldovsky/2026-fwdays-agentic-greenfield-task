# Specification: Core Database and Encryption (`core-database`)

## Glossary and Definitions
- **Drizzle ORM**: A lightweight and type-safe TypeScript Object Relational Mapper.
- **Serverless PostgreSQL**: A PostgreSQL database (Neon or Supabase) designed to scale to zero, requiring optimized connection pooling to prevent connection exhaustion.
- **AES-256-GCM**: Advanced Encryption Standard in Galois/Counter Mode, providing both confidentiality and data authenticity (authenticated encryption).
- **IV (Initialization Vector)**: A random 12-byte buffer used to ensure that encrypting the same text twice yields different ciphertexts.
- **Authentication Tag**: A 16-byte buffer generated by AES-GCM to verify data integrity.
- **Combined Encryption Output**: The persisted format of encrypted credentials stored as colon-separated hex strings: `iv_hex:auth_tag_hex:ciphertext_hex`.
- **API Key Hash**: A SHA-256 hash of a cryptographically secure API key used to authenticate client requests.
- **Session / Magic Link Token**: Cryptographically secure, high-entropy random identifiers (UUIDv4) used for authentication.

## Scope & Non-Goals
### Bounded Scope
- Configuration of Drizzle ORM and connection manager with Serverless-ready pooling.
- Definition of database schema tables (`users`, `magic_links`, `sessions`, `subscriptions`, `conversions`) with appropriate indexes.
- Utility module (`lib/crypto.ts`) for AES-256-GCM encryption/decryption of credentials.
- Security-safe storage of API keys (`api_key_hash`) and tokens.

### Non-Goals
- User interface forms for CRM/Telephony credentials (implemented in `dashboard-analytics`).
- Live API synchronization loops with CRMs and Telephony providers (implemented in integrations).
- Scheduling logic for daily conversion log retention cleanup (implemented in `ingestion-api`).

## ADDED Requirements

### Requirement: Database Connection and Drizzle ORM Setup
The system SHALL use Drizzle ORM to establish and manage connections to the PostgreSQL database (Neon or Supabase). The connection manager SHALL handle Serverless environments by reusing connections and preventing connection exhaustion under concurrent requests. It SHALL enforce secure connections using SSL/TLS.

#### Scenario: Database connection initialization in Serverless environment
- **WHEN** the application processes a database query
- **THEN** it SHALL initialize or reuse a single connection client using Drizzle to execute the query without spawning excessive connections.
- **AND** the connection client SHALL enforce SSL/TLS encryption.

### Requirement: Core Schema Definition
The database schema SHALL define tables for `users`, `magic_links`, `sessions`, `subscriptions`, and `conversions` using Drizzle ORM. All schema declarations MUST reside in `db/schema/` and be typed strictly. All database indexes SHALL follow the standard naming convention: `idx_<table_name>_<column_names>`. All foreign key relations targeting `users.id` SHALL configure a cascade delete policy (`onDelete: "cascade"`) to maintain data integrity when user records are deleted.

#### Scenario: User registration table fields
- **WHEN** a query inspects the database schema for the `users` table
- **THEN** it SHALL verify fields for:
  - `id` (UUIDv4 primary key)
  - `telegram_id` (unique, 64-bit bigint, handled as a JS string/BigInt to avoid precision loss)
  - `telegram_username` (nullable varchar)
  - `email` (unique, nullable varchar)
  - `website_url` (nullable varchar)
  - `api_key_hash` (unique varchar storing the SHA-256 hash of the API key)
  - `crm_url` (nullable varchar)
  - `crm_login` (nullable varchar)
  - `crm_password` (encrypted nullable varchar)
  - `telephony_url` (nullable varchar)
  - `telephony_login` (nullable varchar)
  - `telephony_password` (encrypted nullable varchar)
  - `telephony_api_key` (encrypted nullable varchar)
  - `created_at` (timestamp with time zone)
  - `updated_at` (timestamp with time zone)
- **AND** the system SHALL ensure that `telegram_id` (stored as `bigint`) is converted to a `string` (or properly serialized) before sending it in any JSON responses (such as Next.js Route Handlers) to avoid serialization failures.

#### Scenario: Magic Link token table fields
- **WHEN** a query inspects the database schema for the `magic_links` table
- **THEN** it SHALL verify fields for:
  - `id` (UUIDv4 primary key)
  - `user_id` (foreign key to `users.id` with cascade delete)
  - `token` (unique UUIDv4 token identifier)
  - `expires_at` (timestamp with time zone)
  - `is_used` (boolean, default false)
  - `created_at` (timestamp with time zone)

#### Scenario: Session table fields
- **WHEN** a query inspects the database schema for the `sessions` table
- **THEN** it SHALL verify fields for:
  - `id` (UUIDv4 primary key)
  - `user_id` (foreign key to `users.id` with cascade delete)
  - `token` (unique UUIDv4 session identifier)
  - `expires_at` (timestamp with time zone)
  - `created_at` (timestamp with time zone)

#### Scenario: Subscriptions table fields
- **WHEN** a query inspects the database schema for the `subscriptions` table
- **THEN** it SHALL verify fields for:
  - `id` (UUIDv4 primary key)
  - `user_id` (foreign key to `users.id` with cascade delete)
  - `tariff_plan` (enum: 'monthly', 'yearly')
  - `status` (enum: 'active', 'paused', 'suspended', 'cancelled')
  - `wallet_id` (nullable varchar)
  - `card_token` (nullable varchar)
  - `amount` (integer, representing the UAH amount in minor units (kopecks) of the last successful subscription invoice/payment, nullable)
  - `currency` (varchar, ISO 4217 currency code, default '980' for UAH)
  - `last_invoice_id` (nullable varchar)
  - `failed_attempts_count` (integer, default 0)
  - `last_failed_attempt_at` (nullable timestamp with time zone)
  - `current_period_end` (timestamp with time zone)
  - `created_at` (timestamp with time zone)
  - `updated_at` (timestamp with time zone)

#### Scenario: Conversions table fields and indexes
- **WHEN** a query inspects the database schema for the `conversions` table
- **THEN** it SHALL verify fields for:
  - `id` (UUIDv4 primary key)
  - `user_id` (foreign key to `users.id` with cascade delete)
  - `date` (date type)
  - `conversion_time` (timestamp with time zone, stored in UTC)
  - `conversion_name` (varchar)
  - `is_ad_conversion` (boolean)
  - `email` (nullable varchar)
  - `phone` (nullable varchar)
  - `conversion_value` (numeric)
  - `order_id` (nullable varchar)
  - `ip_address` (nullable varchar)
  - `ad_source` (nullable varchar)
  - `channel` (nullable varchar)
  - `created_at` (timestamp with time zone)
- **AND** it SHALL verify that a composite index named `idx_conversions_user_id_conversion_time` exists on `(user_id, conversion_time)` for optimized analytics queries.
- **AND** it SHALL verify that an index named `idx_conversions_conversion_time` (or `idx_conversions_created_at`) exists on `conversion_time` (or `created_at`) for retention-based cleanup queries.

### Requirement: AES-256-GCM Encryption for Sensitive Credentials
The system SHALL encrypt sensitive user configuration fields (specifically `crm_password`, `telephony_password`, and `telephony_api_key`) before persisting them to the database. The encryption algorithm MUST be AES-256-GCM. The system SHALL fail fast if the encryption key is invalid or missing.

#### Scenario: Validation of ENCRYPTION_KEY on application initialization
- **WHEN** the application starts up or the cryptography module is loaded
- **THEN** the system SHALL verify that the `ENCRYPTION_KEY` environment variable is defined.
- **AND** it SHALL verify that the key (provided as a 64-character hex-encoded string) decodes to exactly 32 bytes (256 bits).
- **AND** it SHALL throw a descriptive error preventing startup if these conditions are not met.

#### Scenario: Encryption of user CRM credentials
- **WHEN** a user saves or updates their CRM password
- **THEN** the system SHALL encrypt the CRM password using a key defined in the `ENCRYPTION_KEY` environment variable.
- **AND** it SHALL generate a secure random 12-byte initialization vector (IV) and retrieve the 16-byte authentication tag from the AES-GCM cipher.
- **AND** it SHALL format the output as `iv_hex:auth_tag_hex:ciphertext_hex` and save it to the `crm_password` field.

### Requirement: AES-256-GCM Decryption for Integration Runs
The system SHALL decrypt previously encrypted CRM/telephony credentials using the corresponding key and metadata (IV and tag) when retrieving them from the database to run API sync processes.

#### Scenario: Decryption of telephony API token
- **WHEN** an integration sync task fetches a user's telephony API token from the database
- **THEN** the system SHALL split the stored string by the colon delimiter (`:`) to extract the IV, authentication tag, and ciphertext.
- **AND** it SHALL decrypt the value using `ENCRYPTION_KEY` and verify its integrity using the authentication tag.
- **AND** if decryption or integrity validation fails, it SHALL throw a secure custom exception (e.g. `DecryptionFailedError`) without leaking any cryptographic values or stack traces to external logs, and log the security event locally.
- **AND** on successful decryption it SHALL pass the raw API token to the HTTP client for request authentication.

## Definition of Done (DoD)
1. Drizzle configuration (`drizzle.config.ts`) is generated and points to the schema directory.
2. Connection module `db/index.ts` is implemented and verified to reuse connection clients.
3. Database schemas for all specified tables are created in `db/schema/` and exported via `db/schema/index.ts`.
4. Migration scripts are generated via `npx drizzle-kit generate` and stored in `db/migrations`.
5. Cryptography module `lib/crypto.ts` is implemented, handles AES-256-GCM, validates keys on startup, and passes unit tests.
6. The codebase passes typechecking (`tsc --noEmit`) and linting (`npm run lint`).
