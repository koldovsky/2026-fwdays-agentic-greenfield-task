## Context

Цей документ описує архітектурний дизайн та технічні рішення для системи Telegram-сповіщень адміністратора та користувачів платформи. Головне призначення — забезпечення оперативного сповіщення про події білінгу та зміни стану підписки безпосередньо в Telegram через існуючий Telegram-бот.

## Goals / Non-Goals

**Goals:**
- Забезпечити стабільне відправлення повідомлень адміністратору (`TELEGRAM_ADMIN_CHAT_ID`) про всі ключові події підписки.
- Забезпечити надсилання сервісних повідомлень користувачам (вітання, невдала спроба списання, призупинення/пауза послуг) на основі їхнього Telegram-ідентифікатора.
- Гарантувати дотримання правил бренду: виключно українська мова та спокійний бізнес-тон без знаків оклику.
- Захистити основну бізнес-логіку (оплати, вебхуки, автосписання) від збоїв при відправленні сповіщень.

**Non-Goals:**
- Налаштування користувачем фільтрації або вимкнення окремих сповіщень через веб-кабінет.
- Інтеграція інших каналів зв'язку (SMS, Email, Push-сповіщення).
- Моніторинг доставки повідомлень з боку користувача (наприклад, перевірка чи не заблокував користувач бота).

## Decisions

### 1. Використання HTTP клієнта Fetch для взаємодії з Telegram API
Замість підключення громіздких додаткових бібліотек (як `node-telegram-bot-api`), для надсилання сповіщень використовується прямий виклик методу `sendMessage` Telegram Bot API через вбудовану функцію `fetch` у Next.js Route Handlers.
*   **Альтернативи**: Використання `node-telegram-bot-api`.
*   **Rationale**: Прямий `fetch` є легкою, швидкою операцією, яка не створює зайвих залежностей та ідеально працює в Serverless-середовищі (Vercel Edge / Serverless Functions).

### 2. Ізоляція помилок відправлення (Graceful Error Handling)
Усі виклики функцій надсилання сповіщень (`sendAdminAlert`, `sendUserAlert`) огортаються в блоки `try/catch`. Помилка доставки сповіщення ніколи не повинна зупиняти транзакцію оплати або викликати помилку `500` на вебхуку чи в Cron-задачі.
*   **Rationale**: Доставка сповіщення є другорядною задачею, тоді як фіксація оплати або оновлення статусу в БД є критично важливими бізнес-операціями.

### 3. Збір та агрегація даних
Для сповіщення адміністратора використовується комбінований підхід:
- Ім'я, телефон та час беруться безпосередньо з вебхуку Monobank (що гарантує їхню точність на момент оплати).
- Email, сайт та Telegram username завантажуються з бази даних користувачів.
*   **Rationale**: Monobank не знає email або сайт користувача в нашій системі, а наша база даних може не мати актуального імені чи телефону, які користувач вказав при оплаті карткою.

### 4. Контроль тону та мови повідомлень
Усі текстові шаблони зафіксовані в коді українською мовою. Символи знаків оклику (`!`) повністю виключені з шаблонів повідомлень для дотримання правила `BC-BRAND-01` та забезпечення нейтрального тону.

## Risks / Trade-offs

- **[Risk]** Користувач заблокував бот, що призводить до помилки Telegram API `403 Forbidden`.
  *   **Mitigation**: Помилка логується в системні логи сервісу (`console.error`), але не впливає на життєвий цикл підписки користувача.
- **[Risk]** Не налаштовані змінні оточення `TELEGRAM_BOT_TOKEN` або `TELEGRAM_ADMIN_CHAT_ID`.
  *   **Mitigation**: Система здійснює перевірку наявності змінних, у разі відсутності виводить попередження (`console.warn`) та безпечно виходить з функції без генерування критичних виключень.
