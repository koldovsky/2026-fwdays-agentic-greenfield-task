## Context

`categories` is the second capability in Cadence and the first user-owned **data** capability after
the auth boundary of slice 001. It is authored before any code, against
[`docs/requirements.md`](../../../docs/requirements.md) (FR-CAT-01..03), architecture §2.1 (the
`categories` table) and §7 (delete = archive, the O-4 decision), and DESIGN §7.4 (the Categories
screen). Where architecture or DESIGN already decided something, this design follows it; genuine gaps
are listed under Open questions rather than invented here.

## Goals / Non-Goals

**Goals:**
- Per-user create, read (list), edit, and delete of categories: name, color, optional description, a
  flat list with no nesting.
- Delete = archive (soft-delete) so a history-referenced category is never destroyed; archived
  categories drop out of the active list that pickers will consume.
- Reuse — never re-implement — the slice 001 `CurrentUser` dependency and user_id-scoped repository
  pattern, so isolation is structural.

**Non-Goals:**
- Anything that *consumes* categories: timer, sessions, heatmap, metrics, stats, coach (later slices).
- Unarchive (a trivial future add per architecture §7) and any management surface beyond CRUD.
- The per-card stats (total time, session count) in DESIGN §7.4 and the live-sync `changes_cursor`
  bump on writes (architecture §5) — both depend on later slices (see Open questions).

## Decisions

- **Delete = archive (O-4, architecture §7).** `DELETE /api/categories/{id}` sets `archived_at`
  when the category is referenced by sessions; the row survives as a valid FK target, so metrics and
  history never jump because a label was tidied. A category with no sessions **may** be hard-deleted
  (no history to preserve). Rationale is architecture §7: block / reassign / cascade are all worse
  than archive for a data product.
- **Partial-unique-index semantics.** The table's `UNIQUE(user_id, name) WHERE archived_at IS NULL`
  (architecture §2.1) means: (a) uniqueness is per user, so two users may each own a "Work"; (b) a
  user cannot hold two **active** categories with the same name (create and rename both 409 on a
  collision); (c) because the index is partial, an **archived** category never blocks a create — a
  user may archive "Work" and then create a fresh active "Work". The API surfaces a collision as
  `409`, not a 500 from the DB constraint.
- **Isolation by reuse (FR-AUTH-07).** Every `CategoryRepo` method takes `user_id` from the
  `CurrentUser` dependency and scopes every query by it, following the rule slice 001 established. A
  category id owned by another user is simply not returned by the scoped query, so cross-user edit or
  delete yields `404` (not 403) — the row's existence is not revealed.
- **HTTP contract.** `201` create · `200` edit · `204` delete (for both archive and hard-delete) ·
  `409` on a duplicate active name (create or rename) · `404` on a category the user does not own.
  For delete, the archive-vs-hard-delete distinction is server-side (DB state and the active list),
  not signaled by the status code.
- **Color is a hex string** (architecture §2.1, `color TEXT NOT NULL`), produced by the native color
  input of DESIGN §7.4; `description` is nullable; `name` is required. The read surface
  `GET /api/categories` returns only active (`archived_at IS NULL`) categories.
- **Migration.** One Alembic migration `0002_categories` creates the table per architecture §2.1 with
  the standard `id BIGINT GENERATED ALWAYS AS IDENTITY` PK and `created_at`, the `user_id` FK, and the
  partial unique index; the autogenerated SQL is hand-reviewed (partial indexes and IDENTITY usually
  need a manual touch-up), per AGENTS.md.

## Risks / Trade-offs

- Archived categories accumulate over time; acceptable at personal scale, and unarchive is a cheap
  future add. The active list stays clean because it filters on `archived_at IS NULL`.
- Returning `404` (rather than `403`) on cross-user access avoids leaking existence but can read as
  "not found" while debugging; this is the intended consequence of the user_id-scoped pattern.
- The delete branch's "has sessions?" test and the "archived category preserves history" guarantee
  cannot be fully exercised until the `sessions` table exists (later slice) — see Open questions 1.
  The archive **mechanic** itself (set `archived_at`, then excluded from `GET`) is fully testable in
  this slice without any session row.

## Open questions

Surfaced for the owner to resolve at ratification; not silently resolved in a scenario.

1. **Sessions-table sequencing.** FR-CAT-03's "archive when it has sessions, else may hard-delete"
   references the `sessions` table (architecture §2.1), which does not exist until the sessions
   slice. So in slice 002 the "has sessions" predicate has nothing to query. Recommended (owner to
   confirm): slice 002 **always archives** on delete — fully compliant, since hard-delete is only
   permitted, not required — and the hard-delete-when-empty optimization plus its test land with (or
   after) the sessions slice. The scenarios above document the ratified end-state contract either way.
2. **Picker consumption.** Architecture §7 says archived categories "disappear from pickers" (timer,
   save modal, manual add, extension). Those pickers are later slices. Slice 002 delivers only the
   server-side guarantee (`GET /api/categories` returns active-only); confirm the picker UIs
   consuming it are out of scope here.
3. **Category card stats.** DESIGN §7.4 shows per-card "total time" and "session count", which
   consume session data (later slice). Until then they have nothing to sum. Confirm the Categories
   screen ships in slice 002 with zero/placeholder stats rather than waiting on sessions.
4. **Live-sync cursor.** Architecture §5 states any category write bumps the per-user
   `changes_cursor`. That cursor and `GET /api/sync/state` are the sync slice. Slice 002 does not
   wire the bump; confirm it is added with the sync slice.
5. **Server-side color validation.** Architecture §2.1 stores `color` as hex but does not specify
   whether the API validates the hex format server-side (the native color input already emits
   `#rrggbb` client-side). Flagged rather than inventing a specific validation rule.
