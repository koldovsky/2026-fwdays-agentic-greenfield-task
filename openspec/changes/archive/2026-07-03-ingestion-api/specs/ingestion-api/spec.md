## Glossary

| Термін | Визначення |
| :--- | :--- |
| **Конверсія** | Одна подія взаємодії користувача з бізнесом (дзвінок, замовлення, заявка тощо), передана з Google Таблиці через Apps Script. Одиниця збереження — один рядок у таблиці `conversions`. |
| **Активна підписка** | Бізнес-концепція: підписка вважається активною, якщо одночасно виконуються дві умови — поле `status` у БД дорівнює `'active'` **І** `currentPeriodEnd > NOW()`. Важливо: поле `status = 'active'` у БД може зберігатися навіть після закінчення `currentPeriodEnd` (Cron ще не встиг оновити статус). Тому обидві умови перевіряються окремо в коді — недостатньо перевірити лише `status`. Всі інші комбінації вважаються неактивними. |
| **API-ключ** | Секретний токен довжиною ≥ 32 символів, що зберігається у клієнта (Apps Script). У системі зберігається лише його SHA-256 хеш у полі `users.api_key_hash`. |
| **Пакет конверсій** | Масив від 1 до 500 об'єктів конверсій, що передається в одному HTTP-запиті до `POST /api/conversions`. |
| **14 місяців** | SQL-вираз `NOW() - INTERVAL '14 months'` (PostgreSQL). Еквівалент не є фіксованою кількістю днів — використовується саме `INTERVAL '14 months'`. |
| **Vercel Cron Job** | Вбудований планувальник Vercel, який надсилає `GET`-запит до зазначеного шляху за розкладом із `vercel.json`. Запит містить заголовок `Authorization: Bearer <CRON_SECRET>`, де `CRON_SECRET` — змінна середовища, налаштована у Vercel. |

## ADDED Requirements

### Requirement FR-API-01: API ендпоінт прийому конверсій
Система SHALL надавати ендпоінт `POST /api/conversions` для отримання масивів записів конверсій від Google Apps Script. Ендпоінт SHALL приймати JSON-тіло запиту з масивом об'єктів конверсій та повертати JSON-відповідь зі статусом операції.

**Обмеження запиту:**
- Запит MUST містити заголовок `Content-Type: application/json`.
- Максимальний допустимий розмір тіла запиту: 4 МБ (обмеження Next.js App Router Route Handler за замовчуванням). Запити, що перевищують цей розмір, будуть відхилені платформою до досягнення обробника.

#### Scenario: Успішний прийом пакету конверсій
- **WHEN** Apps Script надсилає `POST /api/conversions` з валідним `X-API-Key` та масивом від 1 до 500 записів конверсій
- **THEN** система зберігає усі записи в таблиці `conversions`, пов'язуючи їх з `userId` власника ключа, та повертає `200 OK` з полями `{ "status": "ok", "inserted": <кількість> }`

#### Scenario: Порожній масив конверсій
- **WHEN** Apps Script надсилає `POST /api/conversions` з порожнім масивом `[]`
- **THEN** система повертає `400 Bad Request` з повідомленням `{ "error": "conversions array must contain at least 1 and at most 500 items" }`

#### Scenario: Перевищення ліміту пакету
- **WHEN** Apps Script надсилає масив з більш ніж 500 записами конверсій
- **THEN** система повертає `400 Bad Request` з повідомленням `{ "error": "conversions array must contain at least 1 and at most 500 items" }`

### Requirement FR-API-02: Автентифікація запитів за API-ключем
Система SHALL автентифікувати кожний запит до `POST /api/conversions` за допомогою заголовка `X-API-Key`. Ключ SHALL хешуватися за допомогою SHA-256 та порівнюватися з полем `api_key_hash` у таблиці `users`.

#### Scenario: Запит з валідним API-ключем
- **WHEN** запит містить заголовок `X-API-Key` зі значенням, SHA-256 хеш якого відповідає `api_key_hash` існуючого користувача
- **THEN** система ідентифікує користувача та продовжує обробку запиту

#### Scenario: Запит без заголовка X-API-Key
- **WHEN** запит не містить заголовка `X-API-Key`
- **THEN** система повертає `401 Unauthorized` з повідомленням `{ "error": "Missing X-API-Key header" }`

#### Scenario: Запит з невалідним API-ключем
- **WHEN** запит містить заголовок `X-API-Key`, але його SHA-256 хеш не відповідає жодному `api_key_hash` у таблиці `users`
- **THEN** система повертає `401 Unauthorized` з повідомленням `{ "error": "Invalid API key" }`

### Requirement FR-API-03: Перевірка активності підписки
Система SHALL перевіряти статус підписки користувача перед прийомом даних. Якщо підписка відсутня або неактивна, запит SHALL бути відхилено.

#### Scenario: Користувач з активною підпискою
- **WHEN** автентифікований користувач має підписку зі статусом `active` та `currentPeriodEnd` у майбутньому
- **THEN** система приймає та обробляє дані конверсій

#### Scenario: Користувач з підпискою у статусі paused
- **WHEN** автентифікований користувач має підписку зі статусом `paused`
- **THEN** система повертає `402 Payment Required` з повідомленням `{ "error": "Subscription is paused. Please resume your subscription." }`

#### Scenario: Користувач з підпискою у статусі suspended
- **WHEN** автентифікований користувач має підписку зі статусом `suspended`
- **THEN** система повертає `402 Payment Required` з повідомленням `{ "error": "Subscription is suspended due to payment failure." }`

#### Scenario: Користувач з підпискою у статусі cancelled
- **WHEN** автентифікований користувач має підписку зі статусом `cancelled`
- **THEN** система повертає `403 Forbidden` з повідомленням `{ "error": "Subscription has been cancelled." }`

#### Scenario: Користувач з підпискою у статусі created
- **WHEN** автентифікований користувач має підписку зі статусом `created` (створена, але оплата ще не підтверджена)
- **THEN** система повертає `403 Forbidden` з повідомленням `{ "error": "Subscription is not yet activated. Please complete your payment." }`

#### Scenario: Користувач зі статусом active, але закінченим періодом
- **WHEN** автентифікований користувач має підписку зі статусом `active`, але `currentPeriodEnd` вже минув
- **THEN** система повертає `402 Payment Required` з повідомленням `{ "error": "Subscription period has expired." }`

#### Scenario: Користувач без жодної підписки
- **WHEN** автентифікований користувач не має жодного запису в таблиці `subscriptions`
- **THEN** система повертає `403 Forbidden` з повідомленням `{ "error": "No active subscription found." }`

### Requirement FR-API-04: Валідація та нормалізація схеми конверсії
Система SHALL валідувати кожний запис конверсії відповідно до визначеної схеми даних. Невалідні записи SHALL бути відхилені разом з усім пакетом.

> **Примітка щодо назв полів**: JSON-контракт API використовує camelCase (наприклад, `conversionTime`, `conversionName`, `isAdConversion`). Назви полів у FR-API-04 є human-readable описами, а не JSON-ключами.

**Схема об'єкта конверсії (JSON):**

| JSON-ключ | Тип | Обов'язкове | Опис |
| :--- | :--- | :---: | :--- |
| `date` | string (YYYY-MM-DD) | так | Дата конверсії |
| `conversionTime` | string (ISO 8601) | так | Точний час конверсії |
| `conversionName` | string (непорожній після trim) | так | Назва типу конверсії. Валідний, якщо містить хоча б один не-пробільний символ. Рядки, що складаються виключно з пробільних символів (`" "`, `"\t"` тощо), вважаються невалідними. |
| `isAdConversion` | boolean | так | Чи є конверсія рекламною |
| `email` | string | ні | Email клієнта |
| `phone` | string | ні | Телефон клієнта |
| `conversionValue` | number | ні | Цінність конверсії |
| `orderId` | string | ні | Ідентифікатор замовлення |
| `ipAddress` | string | ні | IP-адреса клієнта |
| `adSource` | string | ні | Рекламне джерело |
| `channel` | string | ні | Канал конверсії |

#### Scenario: Запис з усіма обов'язковими полями
- **WHEN** запис конверсії містить обов'язкові поля `date` (YYYY-MM-DD), `conversionTime` (ISO 8601), `conversionName` (непорожній після trim рядок) та `isAdConversion` (boolean)
- **THEN** система приймає запис та зберігає його з усіма обов'язковими та наданими необов'язковими полями

#### Scenario: Запис без обов'язкового поля
- **WHEN** запис конверсії не містить одного або більше обов'язкових полів (`date`, `conversionTime`, `conversionName`, `isAdConversion`)
- **THEN** система повертає `400 Bad Request` з повідомленням `{ "error": "Validation failed", "details": [<масив об'єктів помилок>] }` — жодний запис з пакету не зберігається (транзакційна семантика: все або нічого)

**Формат елемента масиву `details`:**
```json
{ "index": 2, "field": "conversionTime", "message": "must be a valid ISO 8601 timestamp" }
```
Де `index` — позиція запису в масиві (0-based), `field` — назва поля з помилкою, `message` — опис помилки.

#### Scenario: Невалідний формат дати
- **WHEN** поле `date` не відповідає формату `YYYY-MM-DD` або `conversionTime` не є валідним ISO 8601
- **THEN** система повертає `400 Bad Request` з відповідною помилкою валідації — жодний запис не зберігається

#### Scenario: Транзакційна семантика пакету
- **WHEN** хоча б один запис у пакеті не проходить валідацію
- **THEN** система відхиляє весь пакет та повертає `400 Bad Request` з деталями помилок; жодний запис не записується до таблиці `conversions` (rollback)

#### Scenario: Необов'язкові поля
- **WHEN** запис конверсії містить необов'язкові поля (`email`, `phone`, `conversionValue`, `orderId`, `ipAddress`, `adSource`, `channel`)
- **THEN** система зберігає їх у відповідних колонках таблиці `conversions`; пропущені поля зберігаються як `null`

#### Scenario: Конверсія з `conversionTime` у майбутньому
- **WHEN** запис конверсії містить `conversionTime`, що вказує на момент часу більш ніж на 24 години у майбутньому відносно поточного серверного часу
- **THEN** система повертає `400 Bad Request` з відповідною помилкою валідації (`"conversionTime must not be more than 24 hours in the future"`) — жодний запис з пакету не зберігається

#### Scenario: Конверсія з `conversionTime` у далекому минулому
- **WHEN** запис конверсії містить `conversionTime`, що відповідає валідному ISO 8601, але старіший за 14 місяців відносно поточного серверного часу
- **THEN** система приймає та зберігає запис без помилки. Такий запис буде видалений Cron-задачею очищення при наступному запуску (FR-API-05). Це задумана поведінка — API не відповідає за фільтрацію за давністю, лише за валідність формату.

### Requirement NFR-PERF-01: Продуктивність API
Ендпоінт `POST /api/conversions` SHALL відповідати протягом ≤ 200 мс на p95 для пакетів до 100 записів. Для пакетів від 101 до 500 записів цільовий показник — ≤ 500 мс на p95. Ці цільові показники не враховують Vercel cold start (перший запит після неактивності). Система SHALL використовувати batch insert для мінімізації кількості запитів до бази даних.

#### Scenario: Пакет до 100 записів
- **WHEN** Apps Script надсилає пакет з 100 валідних записів конверсій
- **THEN** система обробляє запит та відповідає протягом 200 мс на p95

#### Scenario: Пакет від 101 до 500 записів
- **WHEN** Apps Script надсилає пакет від 101 до 500 валідних записів конверсій
- **THEN** система обробляє запит та відповідає протягом 500 мс на p95

#### Scenario: Batch insert
- **WHEN** система записує масив конверсій у базу даних
- **THEN** система SHALL виконувати один batch `INSERT` замість окремих запитів на кожний запис

### Requirement FR-API-05: Автоматичне очищення застарілих конверсій
Система SHALL автоматично видаляти записи конверсій, старші за 14 місяців, раз на добу. Очищення SHALL виконуватися фоновим процесом (Vercel Cron Job). SQL-критерій видалення: `conversionTime < NOW() - INTERVAL '14 months'` (PostgreSQL). Щоб уникнути тривалого блокування БД при великих обсягах, видалення SHALL виконуватися пакетами по `LIMIT 10000` з повторними запусками до завершення.

> **Ідемпотентність при примусовому завершенні**: Vercel Serverless функції мають обмеження часу виконання (до 10 секунд на Hobby tier). Якщо під час виконання Cron-задачі функція буде примусово завершена після видалення кількох пакетів, але до завершення всього обсягу — це прийнятна поведінка. Наступний плановий запуск продовжить видалення з того місця, де залишилися записи. Часткове видалення (partial delete) є ідемпотентним і не призводить до пошкодження даних.

#### Scenario: Щоденне очищення
- **WHEN** Cron-задача запускається за розкладом (раз на добу)
- **THEN** система видаляє всі записи з таблиці `conversions`, де `conversionTime < NOW() - INTERVAL '14 months'` пакетами по `LIMIT 10000`, та логує загальну кількість видалених записів

#### Scenario: Відсутність застарілих записів
- **WHEN** Cron-задача запускається, але жодний запис не відповідає умові `conversionTime < NOW() - INTERVAL '14 months'`
- **THEN** система завершує операцію без видалення та логує `0 records deleted`

#### Scenario: Захист Cron-ендпоінта — відсутній заголовок
- **WHEN** зовнішній запит намагається викликати Cron-ендпоінт `GET /api/conversions/cleanup` без заголовка `Authorization: Bearer <CRON_SECRET>`
- **THEN** система повертає `401 Unauthorized`

#### Scenario: Захист Cron-ендпоінта — невалідний токен
- **WHEN** зовнішній запит до `GET /api/conversions/cleanup` містить заголовок `Authorization: Bearer <WRONG_TOKEN>`, значення якого не збігається зі значенням `CRON_SECRET`
- **THEN** система повертає `401 Unauthorized` (не розкриваючи причину невідповідності)

#### Scenario: Захист Cron-ендпоінта — відсутня змінна середовища
- **WHEN** змінна середовища `CRON_SECRET` не задана (порожня або відсутня) і надходить запит до `GET /api/conversions/cleanup`
- **THEN** система повертає `500 Internal Server Error` та логує помилку конфігурації (не розкриваючи значення секрету)

### Requirement FR-API-06: Обробка помилок та відповіді API
Система SHALL повертати стандартизовані JSON-відповіді для усіх випадків (успіх та помилка). API SHALL обробляти несподівані помилки gracefully, не розкриваючи внутрішні деталі реалізації.

#### Scenario: Невалідний JSON у тілі запиту
- **WHEN** тіло запиту не є валідним JSON
- **THEN** система повертає `400 Bad Request` з повідомленням `{ "error": "Invalid JSON body" }`

#### Scenario: Некоректний HTTP-метод
- **WHEN** надходить запит з методом, відмінним від `POST` (наприклад, `GET`, `PUT`, `DELETE`)
- **THEN** система повертає `405 Method Not Allowed`

#### Scenario: Внутрішня помилка сервера
- **WHEN** під час обробки запиту виникає непередбачена помилка (наприклад, збій з'єднання з БД)
- **THEN** система повертає `500 Internal Server Error` з повідомленням `{ "error": "Internal server error" }` без розкриття внутрішніх деталей та логує помилку на сервері
