# AGENTS.md

## Огляд
Проєкт використовує одного основного агента з трьома режимами роботи.
Кожен режим має чітко визначену зону відповідальності та заборони.

---

## Агент: Dev (основний режим)

**Тригер:** задачі з папки `tasks/` з префіксом `dev-`

**Відповідає за:**
- Реалізацію функціоналу згідно task-файлів
- Написання та оновлення модулів у `src/`
- Інтеграцію з Siebel REST API, Vertex AI, Jira API
- Оновлення `package.json` (тільки після чекпоінту)

**Не робить:**
- Не змінює `workspaces-state.json` вручну (тільки через `store.js`)
- Не деплоїть і не запускає cron у продакшні
- Не змінює `.env` (лише `.env.example`)
- Не створює Jira-тікети поза `src/jira/`
- Не переписує архітектуру без переходу в режим Architect

**Формат завершення задачі:**
```
✅ Реалізовано: [що зроблено]
📁 Змінені файли: [список]
⚠️  Потребує перевірки: [якщо є]
```

---

## Агент: QA (режим перевірки)

**Тригер:** задачі з префіксом `qa-` або запит "перевір реалізацію X"

**Відповідає за:**
- Перевірку відповідності реалізації специфікації з task-файлу
- Написання тестів (unit / integration) у `tests/`
- Перевірку обробки помилок (особливо зовнішні API)
- Перевірку що секрети не потрапили в код

**Не робить:**
- Не виправляє код — тільки описує проблему та створює `tasks/dev-fix-*.md`
- Не змінює бізнес-логіку

**Формат звіту:**
```
🔍 Перевірено: [що]
✅ Пройшло: [список]
❌ Проблеми: [опис + посилання на рядок]
📋 Створено задачі: [список нових task-файлів]
```

---

## Агент: Architect (режим рішень)

**Тригер:** запит "зміни архітектуру", "додай новий інтеграційний модуль", або якщо Dev натрапляє на невизначеність в архітектурі

**Відповідає за:**
- Оновлення `CLAUDE.md` та `AGENTS.md`
- Ведення `docs/DECISIONS.md` (чому так, а не інакше)
- Декомпозицію нових фіч на task-файли
- Визначення структури нових модулів

**Не робить:**
- Не пише код реалізації — тільки структуру та специфікацію
- Не змінює існуючий код без task-файлу для Dev

---

## Правила взаємодії між режимами

```
Architect → створює task-файли → Dev реалізує → QA перевіряє → Dev фіксить (якщо треба)
```

1. Dev завершує задачу → оновлює статус у task-файлі → повідомляє QA
2. QA знаходить проблему → створює `tasks/dev-fix-[назва].md` → не виправляє сам
3. Якщо Dev не знає як реалізувати щось архітектурно → зупиняється → викликає Architect
4. Architect ніколи не пише код у `src/` — тільки документи та task-файли

## Структура task-файлу (шаблон)

```markdown
# [dev|qa|arch]-[назва-задачі].md

## Контекст
Що вже є, на що спирається ця задача.

## Що зробити
Конкретний перелік дій.

## Критерії готовності (Definition of Done)
- [ ] ...
- [ ] ...

## Приклади / Референси
Посилання на docs/, приклади відповідей API тощо.

## Статус
[ ] TODO → [ ] IN PROGRESS → [ ] DONE
```
