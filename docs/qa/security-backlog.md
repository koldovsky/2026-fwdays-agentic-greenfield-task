# Security backlog (deferred findings)

Real findings surfaced by the review-gate that fall OUTSIDE the slice that surfaced them.
They are recorded here so they are not lost; each becomes a gated hardening slice. Not a
regression from any single feature slice.

| ID | Source slice review | Finding | Severity | Owner / when |
|----|---------------------|---------|----------|--------------|
| SEC-BL-01 | cabinet-shell | No rate limiting / lockout on the sign-in server action (`app/sign-in/actions.ts`); against the single shared HR account this allows online password guessing, and each attempt runs scrypt (CPU DoS vector). | major | auth-hardening slice — per-IP + per-email sliding window with backoff, durable store (Vercel-compatible, e.g. Upstash). Pairs with the deferred add-auth nit #5 (CSRF). |
| SEC-BL-02 | cabinet-shell | Proxy guard trusts the signed access JWT alone; a revoked/deleted HR user keeps access until the short access token expires. No `HrUser.isActive` flag; sessions are only revoked on explicit sign-out and rotation. | major | auth-hardening slice — add account-status, revoke all sessions on deactivation/password change, confirm subject still active on refresh. |
| SEC-BL-03 | cabinet-shell | `npm audit`: 5 moderate transitive advisories — `postcss <8.5.10` (build-time XSS in stringify) under `next 16.2.9`; `@hono/node-server <1.19.13` (serveStatic bypass) under Prisma dev tooling. No critical/high; low real exploitability. | moderate | dependency-maintenance — pin/override `postcss >=8.5.10`; update Prisma dev tooling when a non-breaking fix lands. Do NOT run `npm audit fix --force` (it downgrades next/prisma). |
| SEC-BL-04 | cabinet-shell (contested) | Sign-out POST (`app/api/auth/sign-out`) has no CSRF/Origin check; SameSite=Lax allows a top-level cross-site POST to force logout (low impact — logout only). | minor | auth-hardening — validate `Origin`/`Sec-Fetch-Site` (same-origin) on state-changing routes/actions. |
| SEC-BL-05 | add-link | IDOR on cabinet cycle queries: `getCycleById(id)` and `listCycles()` have no HR-user ownership filter (`Cycle` has no `createdByHrUserId`). In MVP single-HR-account this is moot; becomes critical if a second HR account is added without fixing. | high | cycles-hardening — add `createdByHrUserId` column to `Cycle`, scope all cabinet cycle queries to the authenticated HR user. |
| SEC-BL-06 | add-link | Cycle `token` (43-char opaque bearer credential) is serialised into RSC client HTML payload when passed to `CopyLinkButton` (client component). Any authenticated HR user can extract the token from browser DevTools / page source. Cabinet is auth-guarded, so real exposure is limited to authenticated HR users only; accepted in MVP. | medium | auth-hardening — consider a server action that copies the URL without exposing the raw token to the client bundle, or explicit RSC prop annotation. |
| SEC-BL-07 | add-link | Subject first name is rendered in the respondent page (`Вітаємо, {name}`) and tied to the cycle token. If the token leaks via browser history or Referer, the first name is exposed. Accepted per BC-PRIVACY-02 (deliberate design). | medium | privacy-hardening — add `Referrer-Policy: no-referrer` header for `/respond/*` routes; consider omitting the name if usability allows. |
| SEC-BL-08 | add-usage-accounting | `costUsd` stored as IEEE-754 `Float` (Postgres `float8`); in-process JS `+` accumulates rounding error across many rows. Imperceptible per-row but visible at scale. | major | schema-hardening — change `UsageRow.costUsd` to `Decimal` (Postgres `numeric`) in a migration; adjust `cost()` return type and aggregation query to use `SUM()` in DB. |
| SEC-BL-09 | add-usage-accounting | Single-layer auth on `/usage`: relies solely on the proxy middleware; no in-component fallback `redirect("/sign-in")` if proxy matcher is ever widened. Accepted per project architecture convention (proxy is the gate for all cabinet routes). | medium | auth-hardening — add defense-in-depth `getCurrentHrUser()` → redirect in `UsagePage` when the multi-HR-account slice lands. |
| SEC-BL-10 | add-usage-accounting | `recordUsage` performs no `cycleId` ownership check. Since it is `server-only` and only called from internal AI pipeline code (never from a public endpoint), the attack surface is limited to server-side code execution. Will need a verify step if ever exposed via a server action. | medium | usage-hardening — add cycle existence/ownership assertion before `db.usageRow.create` when the ai-interview slice wires the call. |
| SEC-BL-11 | add-ai-interview | Respondent identity is not modelled — the only name available is the assessment **subject's** first name, used to greet the respondent (form, interview, and landing all do this). In a multi-reviewer 360 the respondent is not the subject, so the greeting name can be wrong. Accepted in the single-respondent MVP; the interview prompt no longer asserts the name IS the respondent's identity. | low | 360-hardening — model respondent identity when multi-reviewer 360 lands; greet by the respondent's own first name. |
| SEC-BL-12 | add-ai-interview | The interview Route Handler has no server-side single-flight guard per cycle: two concurrent POSTs for one cycle can each call the model and last-writer-wins on `Dialog.messages` (one turn's transcript lost). `recordAnswer` is idempotent (unique `(responseId, questionId)` upsert) and the `done` transition is guarded, so answers/status stay correct; only transcript fidelity is at risk. The chat UI disables input while streaming and the MVP is single-respondent, so it is not reachable in normal use. | low | ai-hardening — add a per-cycle in-flight lock (advisory lock or a `Dialog` version column with optimistic concurrency) when multi-respondent lands. |
