# PRD — Планувальник ресурсних центрів виробництва (APS)

**Версія:** 0.3 · **Дата:** 2026-06-24 · **Статус:** proposed  
**Автор:** _[вказати]_ · **Узгоджено з:** плановик, технолог

---

## Мета продукту

Веб-застосунок класу APS (Advanced Planning & Scheduling) для планувальника/технолога.  
Система отримує з 1С замовлення клієнтів, структуру виробів (BOM), технологічні маршрути (МК),
залишки та план надходжень матеріалів — і автоматично будує оптимальний розклад виробничих
операцій по всьому дереву виробу (готовий виріб → підзбірки → деталі).

Операції в МК прив'язані до **груп РЦ** (ГРЦ); система сама розподіляє операції між
конкретними РЦ всередині групи для вирівнювання завантаження.

**Ключові цілі оптимізації (в порядку пріоритету):**
1. Виконати всі замовлення клієнтів у строк
2. Мінімізувати простій обладнання (РЦ)
3. Мінімізувати незавершене виробництво (WIP)

### Побудова розкладу (capability `scheduling`)

#### Горизонт планування

| ID | Опис | Статус |
|---|---|---|
| FR-SCHED-01 | Користувач обирає горизонт планування перед запуском: **3 тижні / 3 місяці / до кінця поточного року**; операції що виходять за горизонт позначаються окремо | proposed |

#### Логіка розміщення

| ID | Опис | Статус |
|---|---|---|
| FR-SCHED-02 | Планування виконується методом **зворотного розкладу (backward scheduling)**: від кінцевої дати замовлення назад по дереву BOM і маршруту | proposed |
| FR-SCHED-03 | Якщо backward scheduling дає старт раніше поточної дати — система автоматично переходить на **forward scheduling** і фіксує прогнозоване запізнення для цього замовлення | proposed |
| FR-SCHED-04 | **Міжопераційний час:** наступна операція в маршруті може стартувати не раніше початку **наступного робочого дня** після завершення попередньої | proposed |
| FR-SCHED-05 | Операція на вузлі-батьку не стартує раніше початку наступного робочого дня після завершення всіх операцій дочірніх вузлів | proposed |
| FR-SCHED-06 | Операція не стартує якщо потрібний матеріал відсутній і не надійде до моменту старту згідно плану надходжень | proposed |

#### Розподіл по групах РЦ

| ID | Опис | Статус |
|---|---|---|
| FR-SCHED-07 | Операція в МК прив'язана до ГРЦ; система призначає її на конкретний РЦ всередині ГРЦ що: (а) має тип операції в переліку дозволених, (б) має найменше завантаження в потрібний часовий слот | proposed |
| FR-SCHED-08 | Якщо всі РЦ ГРЦ перевантажені в потрібний слот — операція ставиться у чергу на найраніший вільний слот серед усіх РЦ ГРЦ | proposed |
| FR-SCHED-09 | Пріоритет при конкуренції операцій за слот на РЦ визначається за **Critical Ratio (CR)** = (дата здачі − сьогодні) / (залишкова трудомісткість в днях); менший CR — вищий пріоритет | proposed |

#### Критичний шлях і варіанти

| ID | Опис | Статус |
|---|---|---|
| FR-SCHED-10 | Система визначає критичний шлях для кожного замовлення — ланцюжок операцій що визначає найранішу дату готовності | proposed |
| FR-SCHED-11 | Система генерує **2 варіанти розкладу**: «мінімум запізнень» (CR-пріоритет) і «мінімум простоїв РЦ» (заповнення слотів без пробілів); користувач порівнює і обирає | proposed |
| FR-SCHED-12 | Перепланування запускається вручну; попередній прийнятий розклад зберігається і не перезаписується автоматично | proposed |
| FR-SCHED-13 | Користувач може закріпити операцію на конкретний РЦ і/або часовий слот; закріплені операції не переміщуються при перерахунку | proposed |

## Концептуальна модель даних

```
Замовлення клієнта  [дата здачі, пріоритет]
  └── Виріб  [BOM верхній рівень, кількість]
        ├── Підзбірка A  [кількість]
        │     ├── Деталь A1  → МК → [Оп.10 (ГРЦ-01), Оп.20 (ГРЦ-03)]
        │     └── Деталь A2  → МК → [Оп.10 (ГРЦ-02)]
        └── Підзбірка B  [кількість]
              └── Деталь B1  → МК → [Оп.10 (ГРЦ-01), Оп.20 (ГРЦ-04)]

Група РЦ (ГРЦ)
  ├── РЦ-01  [потужність, дозволені типи операцій, календар]
  └── РЦ-02  [потужність, дозволені типи операцій, календар]

Операція в розкладі:
  - належить до МК конкретної номенклатури
  - прив'язана до ГРЦ (з МК) → призначена на конкретний РЦ (планувальником)
  - тривалість = норма (хв/шт) × кількість
  - старт не раніше: наступний роб. день після фінішу попередньої операції
  - старт не раніше: наступний роб. день після фінішу всіх операцій дочірніх вузлів BOM
  - старт блокується при дефіциті матеріалу
```

## Алгоритм планування (верхній рівень)

```
ВХІД: замовлення[], BOM[], маршрути_МК[], групиРЦ[], залишки[], надходження[], горизонт

ФАЗА 1 — MRP (розрахунок потреб)
  1. Розгорнути BOM для всіх замовлень → дерево вузлів із кількостями
  2. Розрахувати брутто-потребу в куплених матеріалах
  3. Розрахувати нетто-дефіцит = брутто − залишки − надходження
  4. Позначити операції з незакритим дефіцитом як заблоковані

ФАЗА 2 — APS (розклад операцій)
  5. Топологічне сортування вузлів BOM (листя → корінь)
  6. Для кожного вузла зібрати операції МК, розрахувати тривалість (хв × кількість)
  7. Backward scheduling: від дати замовлення назад, з урахуванням міжопераційного дня
  8. При конфлікті на РЦ всередині ГРЦ — обрати РЦ з мінімальним завантаженням
  9. При конкуренції кількох операцій за один РЦ — пріоритет за CR (менший = вищий)
  10. Якщо backward дає старт < сьогодні → switch to forward, зафіксувати запізнення
  11. Визначити критичний шлях для кожного замовлення

ВАРІАНТ 2 (сценарій «мінімум простоїв»):
  12. Повторити кроки 7-11 з пріоритетним правилом «заповни слот» замість CR

ВИХІД: розклад_варіант_1, розклад_варіант_2, метрики[]
```

## Поза межами MVP

- Прямий API-коннектор до 1С (HTTP-сервіс або COM) — у MVP лише файловий обмін
- Автоматичне перепланування при змінах в 1С в реальному часі
- Облік часу переналагодження між операціями різних типів (setup matrix)
- Облік браку і повторних операцій (rework loops)
- Мобільний інтерфейс для цеху (змінне завдання на планшеті)
- Авторизація, ролі та журнал змін
- Інтеграція з OEE-системою (фактичні показники РЦ замість нормативних)
- Оптимізація за вартістю (вартість простою, вартість запізнення)
- Багатокритеріальна оптимізація (Pareto-фронт варіантів)
