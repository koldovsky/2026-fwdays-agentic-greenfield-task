- `back-end/src/tv/token-store.ts` (new): XDG-aware path (`$XDG_CONFIG_HOME/mytv/tokens.json` or `~/.mytv/tokens.json`). Atomic write via `.tmp` sibling + `chmod 0o600` + `rename`, so a reader never sees a world-readable copy. In-memory cache warmed on first `loadTokens()`.
- `back-end/src/tv/jsonrpc.ts` (new): thin JSON-RPC 2.0 client on `undici.Pool` per TV origin (`keepAliveTimeout: 30_000`, `keepAliveMaxTimeout: 300_000`, `pipelining: 1`, `rejectUnauthorized: false` — Samsung TVs present self-signed certs on the LAN, spec §1.3). Every request/response logs the `rpcId` for correlation; `AccessToken` is merged into `params` but stripped by the recursive redactor in `logger.ts`. Injectable `JsonRpcTransport` interface — tests never touch a real socket.
- `back-end/src/tv/session.ts` (new): per-TV actor. Owns one transport + one `p-queue` (concurrency 1 — spec says batching is not guaranteed and the samsung-ip-control-protocol skill mandates per-TV serialization). State machine per design D1: `Disconnected → Connecting → Connected → Reconnecting → Connected|Disconnected`, with `Offline` reachable from any state via discovery. `tryOpen()` verifies the transport by calling the heartbeat method once, so an "opened" session that immediately fails is recognized as a failed connect and rolled into the reconnect budget (without this, a broken TV could infinite-loop between Connected → Reconnecting → Connected because the attempt counter never rolled). Reconnect backoff `[200, 500, 1000, 2000, 5000]` ms, cap 5 → `Disconnected`. Heartbeat = `getSystemInfo` every 15 s.
- `back-end/src/tv/manager.ts` (new): `Map<UDN, Session>` with `deviceIndex: Map<UDN, Device>` primed from `registry.snapshot()` + subscribed to `added` / `updated` / `offline` / `removed`. On `offline` the manager calls `session.markOffline()` (state → Offline); on `updated` for an Offline UDN it calls `session.markBackOnline()` (state → Disconnected, no auto-reconnect — user must POST `/connect` per spec).
- `back-end/src/routes/sessions.ts` (new): `GET /api/devices/:udn/session`, `POST /api/devices/:udn/connect`, `POST /api/devices/:udn/disconnect`. Responses go through `toClientSessionState()` so `Reconnecting` never leaves the back-end. `GET` for an unknown UDN returns `{ state: "Disconnected" }` (spec: "unknown or never-connected UDN"), `POST /connect` for an unknown UDN returns a 404 with the JSON error envelope.

**What was done — hotfix on top of `mdns-advertisement` (C2): silence bonjour-service probe noise and wire real shutdown signals**
- Symptom during a real `back:dev` run: bonjour-service dumped `Error: Service name is already in use on the network` (raw `console.log(new Error(...))` from `node_modules/bonjour-service/dist/lib/registry.js:32`, bypassing Pino) whenever a stale `mytv` record was still cached on the LAN from a previous session. - **Fix 2** (`back-end/src/index.ts`): added `SIGINT`/`SIGTERM` handlers that call `app.close()` so Fastify's `onClose` hook fires — which is what actually runs `mdnsHandle.stop()`, which internally waits ~500 ms for the bonjour goodbye packet to leave the LAN before destroying the client. Without this the previous session's advertisement lingered in peer caches for the record's TTL (5 min for A records here) and every subsequent startup collided with itself. This closes the "advertisement withdraws on shutdown" scenario in `openspec/specs/mdns-advertisement/spec.md` for real signal-driven shutdowns, and it's also the follow-up the `platform-foundation` reviewer flagged (long-lived background loops in later capabilities like `upnp-tv-discovery` need this too).
