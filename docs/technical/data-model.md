# Data model — «Поливайко»

> SQLite + Drizzle (ADR-0001). Schema source: [`db/schema/`](../../db/schema/).
> Migrations: [`db/migrations/`](../../db/migrations/). Applied automatically on
> startup ([`db/client.ts`](../../db/client.ts)) — see [`architecture.md`](./architecture.md).
> Persistence requirement: NFR-DATA-01 / SC-4.

## Entities

One aggregate root (`plants`) with two children that cascade on delete.

```
plants 1 ──< growth_measurements   (FK plant_id ON DELETE CASCADE)
       1 ──< watering_events       (FK plant_id ON DELETE CASCADE)
```

## Delete semantics (SC-5 / FR-PLANT-07 / NFR-DATA-02)

`foreign_keys = ON` is set on the connection ([`db/client.ts`](../../db/client.ts)),
so **only deleting a plant cascades** — atomically removing its own measurements
and waterings at the DB level (unbypassable). Deleting a single measurement or
watering removes only that one row. Every delete is explicit and confirmed in the
UI (NFR-USA-02).

## Derived `lastWateredAt` — no duplicate state

A plant's "last watered" date is **not stored**. It is derived as the latest
`watered_on` via one grouped read `MAX(watered_on) GROUP BY plant_id`
([`lib/reminders/queries.ts`](../../lib/reminders/queries.ts)). The watering
status (healthy / soon / overdue) is then computed from `lastWateredAt +
interval_days` vs today Kiev in the pure
[`lib/reminders/status.ts`](../../lib/reminders/status.ts) (a never-watered plant
is overdue). This keeps the home count, reminder rows, and card/detail pills on
one source of truth (FR-REM-02/07).

List ordering (SC-3): measurement and watering lists are `ORDER BY <date> DESC,
id DESC` (most recent first, deterministic id-desc tie-break).
