## Проєкт

**«Гривня»** — спокійний, україномовний застосунок офіційного курсу НБУ
(Next.js 16.2 / React 19.2 / TypeScript). Один екран: список валют,
конвертер, графік курсу за ~30 днів, фраза про тренд за тиждень. Дані —
виключно відкриті та опенсорсні `NBUStatService`; без бази, авторизації,
cookies, аналітики.

## Які практики Agentic Engineering застосовано

### Контекст-інженерія

[`AGENTS.md`](../AGENTS.md) — це постійний, написаний вручну звід правил,
який читає кожен агент у проєкті першим: фіксація стеку, конвенції модулів
(`lib/` має лишатися без залежності від фреймворку — `TC-PURE-01`),
неспростовні правила коректності (поведінка при помилках, формат локалі,
чесність щодо застарілих дат, тон бренду) і сам цикл по слайсах. Поділ
статичного й динамічного контексту зроблено свідомо: постійні правила
живуть в `AGENTS.md`; усе специфічне для конкретного слайсу — в OpenSpec
change-папках, які архівуються одразу після завершення, тож `AGENTS.md`
ніколи не розбухає. `docs/current-state.md` — це динамічний журнал
передачі стану, який оновлюється на кожній віхі за постійним правилом
самого `AGENTS.md` («підтримуй цей файл актуальним автоматично... без
прохання»).

### Цикли (loop engineering) — не покроковий промптинг

Повторюваний, написаний вручну цикл по слайсах провів усі 8 слайсів
можливостей: пропозиція (OpenSpec-зміна, валідована `--strict` до
написання коду) → реалізація test-first (RED, потім GREEN) → рев'ю двома
незалежними перевіряючими → архівування → коміт із трейлерами
`Slice:`/`Refs:`. Сам цикл, його ворота й ролі агентів **свідомо не
згенеровані готовим фреймворком** — див.
[ADR-0003](../docs/adr/ADR-0003-prior-art-reuse-boundary.md), де
зафіксовано, що саме перевикористано (механізми: CLI OpenSpec, git-хуки,
форма CI), а що написано самостійно (поділ maker/checker, ворота, що
означає «добре» саме для цього застосунку). Ворота G0–G7 в
[CHECKLIST.md](../CHECKLIST.md) — мої власні, підігнані під проєкт, а не
скопійований шаблон.

### Maker ≠ checker

Кожен слайс будувала одна роль (`kurs-maker`, див.
[`.claude/agents/kurs-maker.md`](../.claude/agents/kurs-maker.md)), а
перевіряли дві незалежні ролі, які нічого не будували: `kurs-reviewer`
(відповідність специфікації + коректність) та `kurs-eval-judge` (якісна
оцінка — тон, ясність, чесність). Це відбувалося двічі: один раз на
кожному слайсі (8 разів, `docs/qa/review-findings.md` +
`docs/qa/eval-report.md`, по одному розділу на слайс) і один раз глобально
перед релізом (Stage 10 — обидва перевіряючі заново, «з холодного старту»,
перечитали **весь** застосунок, з прямою інструкцією не довіряти
самоогляду мейкера, `docs/qa/global-review.md`). Глобальний прохід знайшов
реальний наскрізний дефект, якого жодне послайсове рев'ю не могло
побачити: конвертер валют тихо округлював курс до меншої кількості
десяткових знаків, ніж решта застосунку показувала для тієї самої валюти —
виправлено в [`lib/currency/formatRate.ts`](../lib/currency/formatRate.ts),
перевірено наживо в реальному браузері, а не лише підтверджено тестом.

### Верифікація — тести, evals, перевірки, а не «здається, працює»

- **Unit + integration:** 122 тести на Vitest, кожен модуль `lib/`
  написаний test-first (анотації `@trace FR-x` пов'язують кожен тест із
  пронумерованою вимогою), плюс один інтеграційний тест
  ([`convertFlow.integration.test.ts`](../lib/currency/convertFlow.integration.test.ts)),
  який наскрізно компонує реальні модулі без жодних моків.
- **E2E + доступність:** 14 тестів на Playwright проти справжнього
  dev-сервера й **живих даних НБУ** — основний користувацький сценарій,
  адаптивні брейкпоінти (вимірюється фактична обчислена CSS-сітка, а не
  «на око» зі скриншота), та сканування `@axe-core/playwright` за WCAG 2
  A+AA в обох темах. Цей прохід знайшов і виправив три реальні дефекти
  доступності (дві проблеми контрасту, одна відсутня доступна назва поля),
  яких не помітили вісім «чистих» ручних рев'ю — див.
  `docs/qa/automated-verification-latest.md`.
- **Якісні evals:** `evals/cases/*.eval.ts`, по одному рубрику на якісну
  поверхню кожної можливості (український тон, відсутність знаків оклику,
  ясність помилок), оцінювані роллю `kurs-eval-judge` — кожен кейс PASS,
  9/9 областей (8 слайсів + 1 глобальний прохід) розглянуто в
  [`docs/qa/acceptance-report.md`](../docs/qa/acceptance-report.md).
- **Трасування:** `scripts/check-traceability.mjs` (написаний самостійно)
  блокує кожен коміт, якщо хоч одна MVP-вимога не згадана в специфікації;
  детальніша, читабельна матриця трасування
  ([`docs/qa/traceability-matrix.md`](../docs/qa/traceability-matrix.md))
  простежує кожну з 25 MVP-вимог + 1 Future-вимоги аж до реалізації,
  тесту та e2e/eval-доказу.

### Специфікації наперед (SDD)

Кожна можливість була описана в OpenSpec
(`openspec/specs/<capability>/spec.md`) **до** написання коду, валідована
`openspec validate --strict` як pre-commit-ворота. Кожна реальна зміна
слайсу проходила через власну change-папку (`proposal.md`, `design.md`,
`tasks.md`) до початку реалізації, а архівувалась лише після «чистого»
рев'ю обох перевіряючих.

### Власний skill — `kurs-uah`

Окремо від самого застосунку я написав власний, повністю самодостатній
skill — **`kurs-uah`** ([`.claude/skills/kurs-uah/`](../.claude/skills/kurs-uah/)) —
для демонстрації агентного підходу поза межами UI. Це один файл `run.mjs`
(~90 рядків, нуль npm-залежностей — лише вбудований Node `fetch`), який
напряму звертається до офіційного `NBUStatService` НБУ, друкує компактну
українську таблицю курсів (валюта · курс · зміна за період), а **агент
сам розмірковує над цими цифрами**, щоб відповісти природною мовою —
«скільки буде 100 USD у гривнях», «який курс долара», «куди рухається
курс євро». Жодного застосунку, жодної збірки, жодного API-ключа —
достатньо Node і інтернету; та сама папка працює в будь-якому harness
(Claude Code, Cursor, Codex), не лише в цьому проєкті. Skill підпорядкований
тим самим правилам чесності й тону, що й сам застосунок: ніколи не
вигадує курс (лише числа зі скрипту), чесно позначає, якщо останній курс —
за попередній робочий день (вихідний/свято), і відповідає спокійно,
українською, без знаків оклику.

### Інструменти та MCP

Claude Code як основний агентний harness; власні визначення проєкту
`.claude/agents/{kurs-maker,kurs-reviewer,kurs-eval-judge}.md` та
`.claude/commands/{propose-slice,review-slice}.md` задають цикл. Реальна
перевірка в браузері протягом усього проєкту (не лише DOM-асерти) через
MCP-інструмент Claude-in-Chrome — використано, щоб зловити справжній баг
(колізія дублікатних React-ключів при перемиканні валюти) і візуально
підтвердити виправлення контрасту/тем у світлій і темній темі. Playwright +
`@axe-core/playwright` для автоматизованого e2e- та a11y-шару. Жоден
сторонній сервіс рев'ю PR не є частиною самого інженерного циклу —
розділення maker≠checker повністю демонструється власними агентами
проєкту (CodeRabbit рев'ює PR вже потім, як ментор, а не як частина циклу
побудови).

### Що вирішував я, а що — агент

Я визначав скоуп, затверджував обидва контрольні пункти проєкту (фреймінг
продукту, план можливостей), приймав рішення про бренд/тон (спокійний,
україномовний, без знаків оклику — `BC-BRAND-01`), і явно скеровував кожну
стадію («start trend-hint», «let's make Stage 8» тощо) по одній, а не
давав агенту працювати без нагляду від початку до кінця. Агент пропонував
сценарії кожної специфікації з вимог, писав кожен тест і реалізацію
test-first, запускав обидві ролі перевіряючих, знаходив і виправляв
дефекти (зокрема ті, про які я не питав — баг із точністю на Stage 10,
проблеми доступності на Stage 8), і самостійно підтримував журнал передачі
стану (`docs/current-state.md`) та повний QA proof pack за постійними
правилами в `AGENTS.md`.
